# 해시 충돌

해시 함수의 입력 공간은 출력 공간보다 훨씬 큰 경우가 대부분이므로, 서로 다른 키가 같은 버킷 인덱스로 대응되는 <u>해시 충돌</u>은 이론적으로 피할 수 없습니다. 입력이 모든 정수인데 출력은 유한한 배열 인덱스라면, 비둘기집 원리에 따라 여러 정수가 같은 위치를 공유하게 됩니다.

충돌을 처리하지 않으면 조회가 다른 키의 값을 돌려주거나 기존 데이터가 덮어써져 해시 테이블을 신뢰할 수 없게 됩니다. 충돌이 생길 때마다 충돌이 사라질 때까지 배열을 확장할 수도 있지만, 데이터 이동과 모든 해시 재계산이 반복되어 매우 비효율적입니다.

실용적인 구현은 두 원칙을 결합합니다.

1. 충돌이 발생해도 여러 키–값 쌍을 구분하여 정상 동작할 수 있는 저장 구조를 사용합니다.
2. 충돌이 심해져 성능이 떨어질 때만 용량을 확장합니다.

대표적인 충돌 해결 전략은 분리 연결법과 개방 주소법입니다.

## 분리 연결법

<u>분리 연결법</u>은 한 버킷에 하나의 쌍만 두는 대신, 각 버킷을 연결 리스트의 머리로 사용합니다. 같은 인덱스로 해시된 모든 키–값 쌍은 그 리스트의 서로 다른 노드로 저장됩니다.

![분리 연결법 해시 테이블](hash_collision.assets/hash_table_chaining.png)

기본 연산은 다음과 같이 동작합니다.

- **조회**: 해시 함수로 버킷을 찾고, 연결 리스트를 앞에서부터 순회하며 실제 키가 같은 노드를 찾습니다.
- **추가**: 버킷의 리스트에서 같은 키가 있는지 확인합니다. 있으면 값을 갱신하고, 없으면 새 노드를 연결합니다.
- **삭제**: 대응 버킷의 리스트에서 목표 키를 찾아 연결을 끊습니다.

이 방식은 개념이 단순하고 삭제가 자연스럽지만 두 가지 비용이 있습니다. 각 노드가 다음 노드 포인터를 보관하므로 배열만 쓸 때보다 메모리를 더 사용하며, 한 버킷의 리스트가 길어지면 조회가 순차 탐색으로 느려집니다. 또한 흩어진 노드 접근은 연속 배열보다 캐시 지역성이 낮을 수 있습니다.

아래 공식 구현은 설명을 단순하게 하기 위해 연결 리스트 대신 동적 배열을 버킷으로 사용합니다. 전체 테이블은 버킷 배열이고, 각 버킷은 충돌한 쌍의 목록입니다. 적재율이 $\frac{2}{3}$를 넘으면 용량을 $2$배로 늘린 뒤 모든 쌍을 재해싱합니다.

키 분포가 매우 나빠 리스트가 길어지면 조회가 $O(n)$까지 떨어질 수 있습니다. 일부 구현은 일정 길이를 넘은 리스트를 AVL 트리나 레드-블랙 트리로 바꾸어 조회를 $O(\log n)$으로 낮춥니다. 이 전환은 추가 구조 비용이 있으므로 버킷이 충분히 길 때만 이득입니다.

분리 연결법의 성능은 평균 버킷 길이에 좌우됩니다. 적재율이 낮고 해시 값이 고르게 퍼지면 각 리스트가 짧아 거의 즉시 목표를 찾습니다. 반대로 특정 버킷에 키가 집중되면 배열의 다른 빈 공간이 많아도 해당 리스트의 탐색 비용은 커집니다.

## 개방 주소법

<u>개방 주소법</u>은 별도의 연결 구조를 만들지 않고 버킷 배열 자체에서 다른 빈 위치를 탐사합니다. 한 키의 첫 위치가 차 있으면 정해진 규칙으로 다음 후보를 계산하고, 빈 버킷이나 같은 키를 만날 때까지 계속합니다. 선형 탐사, 제곱 탐사, 다중 해싱이 대표적입니다.

개방 주소법에서는 저장과 조회가 반드시 같은 탐사 순서를 사용해야 합니다. 삽입이 충돌 후 세 번째 후보에 값을 놓았다면 조회도 첫 번째부터 같은 후보들을 지나 그 위치에 도달해야 합니다. 중간 상태를 잘못 해석하면 뒤쪽의 키가 존재해도 찾지 못합니다.

### 선형 탐사

선형 탐사는 고정된 간격으로 배열을 순서대로 살핍니다.

- **삽입**: 해시 인덱스가 사용 중이면 보통 $1$칸씩 앞으로 이동하여 첫 빈 버킷에 저장합니다.
- **조회**: 같은 시작점에서 같은 간격으로 이동합니다. 키가 일치하면 값을 반환하고, 한 번도 사용되지 않은 빈 버킷을 만나면 해당 키가 없다고 결론냅니다.
- **갱신**: 탐사 중 같은 키를 만나면 새 버킷을 차지하지 않고 그 값을 바꿉니다.

![선형 탐사를 사용하는 개방 주소 해시 테이블](hash_collision.assets/hash_table_linear_probing.png)

선형 탐사는 구현이 간단하고 연속 메모리를 읽어 캐시에 유리하지만 <u>군집화</u>가 생기기 쉽습니다. 연속해서 찬 구간이 길수록 새 키가 그 구간에 부딪힐 확률이 커지고, 충돌한 키가 구간 끝에 붙으면서 군집이 더 자랍니다. 이 양의 피드백은 삽입·조회·삭제·갱신의 탐사 길이를 계속 늘립니다.

개방 주소 테이블에서는 원소를 단순히 `None`으로 지울 수 없습니다. 조회는 “한 번도 사용되지 않은 빈 버킷”을 만나면 탐사를 멈추기 때문입니다. 충돌로 더 뒤에 배치된 키가 있는데 중간 버킷을 빈 상태로 바꾸면, 조회가 그 앞에서 멈추어 존재하는 키를 없다고 판단합니다.

![개방 주소법에서 직접 삭제가 만드는 조회 오류](hash_collision.assets/hash_table_open_addressing_deletion.png)

해결책은 <u>지연 삭제</u>입니다. 실제로 비우는 대신 `TOMBSTONE` 표식을 남깁니다. 삽입할 때는 이 위치를 재사용할 수 있지만, 조회는 뒤에 목표가 있을 수 있으므로 표식을 만나도 계속 탐사합니다. “미사용 빈 칸”과 “사용했지만 삭제된 칸”의 의미를 분리하는 것입니다.

지연 삭제도 대가가 있습니다. 표식이 쌓이면 실패한 조회조차 많은 칸을 지나야 합니다. 개선 방법으로 탐사 중 처음 만난 묘비 위치를 기억하고, 뒤에서 목표를 발견했을 때 그 원소를 앞쪽 묘비와 교환할 수 있습니다. 조회와 삽입이 반복될수록 원소가 이상적인 시작점에 가까워져 탐사 길이가 줄어듭니다.

배열 끝을 넘어간 탐사는 처음으로 돌아와야 하므로, 구현은 버킷 배열을 원형 배열처럼 취급합니다. 모든 버킷을 한 바퀴 확인했는데 빈 위치가 없다면 확장이 필요합니다.

```python

```

### 제곱 탐사

제곱 탐사는 선형 탐사와 비슷하지만 충돌 횟수의 제곱만큼 이동합니다. 즉 후보 간격은 $1, 4, 9, \dots$처럼 커집니다.

큰 폭으로 건너뛰기 때문에 선형 탐사의 1차 군집화를 완화하고 데이터를 더 넓게 퍼뜨릴 수 있습니다. 그러나 같은 초기 인덱스를 가진 키들이 여전히 같은 후보 열을 따르므로 군집이 완전히 사라지지는 않습니다. 또한 배열 크기와 증가식의 조합에 따라 모든 버킷을 방문하지 못할 수 있습니다. 빈 칸이 있어도 탐사 열에 포함되지 않으면 삽입이 실패하므로, 용량과 탐사식을 함께 설계해야 합니다.

### 다중 해싱

다중 해싱은 여러 해시 함수를 사용합니다. 첫 함수 $f_1(x)$의 위치가 충돌하면 `f_2(x)`, `f_3(x)` 등을 차례로 시도합니다.

- **삽입**: 후보 함수 순서대로 빈 버킷을 찾아 저장합니다.
- **조회**: 동일한 함수 순서로 키를 비교합니다. 목표를 찾으면 값을 반환하고, 사용되지 않은 빈 위치를 만나거나 모든 함수를 소진하면 실패합니다.

선형 탐사보다 후보가 넓게 분산되어 군집화가 덜하지만, 여러 해시 값을 계산하므로 연산 비용이 커집니다. 이중 해싱처럼 두 번째 해시를 탐사 간격으로 사용하면 비교적 적은 함수로 긴 후보 순서를 만들 수 있습니다.

!!! tip

    선형 탐사, 제곱 탐사, 다중 해싱을 포함한 모든 개방 주소 방식은 중간 원소를 단순한 빈 버킷으로 직접 삭제할 수 없습니다. 탐사 연속성을 보존하는 삭제 표식이나 재배치가 필요합니다.

## 프로그래밍 언어의 선택

언어와 표준 라이브러리는 서로 다른 절충안을 선택합니다.

- Python의 `dict`는 개방 주소법을 사용하고, 의사 난수화된 탐사 순서로 충돌을 처리합니다. 연속 배열 기반이라 메모리 지역성이 좋습니다.
- Java의 `HashMap`은 분리 연결법을 사용합니다. JDK 8 이후에는 배열 용량과 버킷 길이가 임계값을 넘으면 연결 리스트를 레드-블랙 트리로 바꾸어 최악의 조회를 완화합니다.
- Go의 맵은 버킷 기반 연결 방식을 사용합니다. 한 버킷에 정해진 수의 쌍을 저장하고 초과분은 오버플로 버킷에 연결합니다. 오버플로가 많아지면 성능 회복을 위해 재배치합니다.

어떤 방식이 절대적으로 우수한 것은 아닙니다. 분리 연결법은 삭제와 높은 적재율에 유리하고, 개방 주소법은 포인터가 적고 캐시 효율이 좋습니다. 라이브러리 사용자는 내부 방식에 의존하기보다 공개된 순서 보장, 키 규칙, 평균 성능 계약을 기준으로 코드를 작성해야 합니다.

충돌 해결 구조를 직접 구현할 때는 성공한 조회만 시험해서는 부족합니다. 같은 해시 값을 가진 여러 키를 연속으로 넣은 뒤 첫째·가운데·마지막 키를 각각 찾고, 존재하지 않는 키도 조회해야 합니다. 삭제 후에는 삭제 위치보다 뒤에 저장된 키가 여전히 검색되는지 확인해야 하며, 배열 끝에서 처음으로 되돌아가는 탐사도 별도 경계 사례로 검사해야 합니다.

확장 테스트에서는 새 용량으로 모든 키가 다시 계산되었는지 확인합니다. 예전 버킷 배열을 그대로 복사하면 일부 키는 새 해시 인덱스와 실제 위치가 달라져 사라진 것처럼 보입니다. 같은 키를 다시 삽입했을 때 원소 수가 늘지 않고 값만 갱신되는지, 묘비 위치를 재사용해도 탐사 경로가 끊기지 않는지도 중요한 불변식입니다.

실제 성능 측정에서는 평균 탐사 길이와 가장 긴 버킷 길이를 함께 관찰하는 것이 유용합니다. 평균이 짧더라도 소수의 심한 군집이 지연 시간의 꼬리를 길게 만들 수 있습니다. 키 분포가 시간에 따라 변하는 서비스라면 적재율만으로 확장을 결정하지 않고, 충돌 횟수나 최대 탐사 길이를 보조 신호로 사용할 수도 있습니다.

보안 관점에서는 공격자가 입력 키를 선택할 수 있는지 살펴야 합니다. 예측 가능한 해시 함수에 충돌 키를 대량으로 보내면 평균적으로 빠른 테이블을 사실상 선형 구조로 만들 수 있습니다. 무작위 시드, 견고한 문자열 해시, 트리 전환 같은 방어는 이런 충돌 집중 공격이 서비스 거부로 이어지는 위험을 줄입니다.

결국 충돌은 예외가 아니라 정상 입력 조건입니다. 올바른 구현은 충돌이 없을 때만 빠른 구조가 아니라, 충돌한 키의 동등성을 정확히 구분하고 삭제·확장 뒤에도 모든 탐사 경로를 보존하는 구조여야 합니다. 이 불변식을 중심으로 설계와 테스트를 구성하면 평균 성능과 정확성을 함께 지킬 수 있습니다.

충돌한 원소가 많아져도 저장된 키와 값은 하나도 유실되어서는 안 됩니다.
