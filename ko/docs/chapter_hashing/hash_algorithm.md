# 해시 알고리즘

앞 절의 분리 연결법과 개방 주소법은 충돌이 생겨도 해시 테이블이 올바르게 동작하도록 만듭니다. 그러나 이 구조들은 충돌의 결과를 처리할 뿐, 충돌이 발생하는 빈도 자체를 줄이지는 못합니다.

충돌이 지나치게 많으면 성능은 급격히 나빠집니다. 분리 연결법에서 이상적인 경우 키–값 쌍이 모든 버킷에 고르게 퍼져 짧은 탐색으로 끝나지만, 최악의 경우 모든 쌍이 한 버킷에 모여 조회가 $O(n)$으로 떨어집니다.

![해시 충돌의 이상적 상황과 최악 상황](hash_algorithm.assets/hash_collision_best_worst_condition.png)

키–값 쌍의 분포는 해시 함수가 결정합니다. 해시 테이블은 먼저 `hash()`로 해시 값을 만들고, 그 값을 배열 길이로 나눈 나머지를 버킷 인덱스로 사용합니다.

```shell
index = hash(key) % capacity
```

용량이 고정되어 있다면 `hash()`의 출력 패턴이 곧 버킷 분포가 됩니다. 따라서 충돌 확률을 낮추려면 충돌 해결 구조뿐 아니라 해시 알고리즘 자체를 설계해야 합니다.

## 해시 알고리즘의 목표

빠르고 견고한 해시 테이블을 만들려면 해시 알고리즘이 다음 성질을 갖추어야 합니다.

- **결정성**: 같은 입력은 언제나 같은 출력을 만들어야 합니다. 저장할 때와 조회할 때 결과가 다르면 원소를 다시 찾을 수 없습니다.
- **높은 효율**: 해시 계산이 충분히 빨라야 합니다. 버킷 접근이 빨라도 키를 변환하는 비용이 크면 전체 연산의 장점이 사라집니다.
- **균등 분포**: 서로 다른 키가 버킷 전체에 가능한 한 고르게 퍼져야 합니다. 분포가 균등할수록 충돌과 평균 탐사 길이가 줄어듭니다.

해시는 해시 테이블 이외의 분야에서도 널리 쓰입니다.

- **비밀번호 저장**: 시스템은 보통 평문 비밀번호를 저장하지 않고 비밀번호에서 계산한 해시와 솔트, 작업 계수를 저장합니다. 로그인 때 입력을 같은 방식으로 처리하여 결과가 일치하는지 확인합니다. 데이터베이스가 노출되어도 평문을 바로 알 수 없게 하는 것이 목적입니다.
- **데이터 무결성 검사**: 송신자가 데이터의 해시를 함께 보내고 수신자가 다시 계산하여 비교합니다. 두 값이 다르면 전송 중 손상되었거나 내용이 바뀌었다는 사실을 알 수 있습니다.
- **콘텐츠 식별**: 파일 내용에서 만든 해시를 이름처럼 사용하면 같은 내용을 중복 저장하지 않거나, 빌드 캐시가 입력 변경 여부를 빠르게 판별할 수 있습니다.
- **디지털 서명**: 큰 문서 전체를 직접 서명하는 대신 고정 길이 해시를 서명하여 계산량을 줄이고 문서 변경을 감지합니다.

암호학적 용도에서는 일반 해시 테이블보다 훨씬 강한 보안 성질이 필요합니다.

- **단방향성**: 출력만으로 입력에 관한 유용한 정보를 역산하기 어려워야 합니다.
- **충돌 저항성**: 같은 해시를 만드는 서로 다른 두 입력을 찾는 일이 계산적으로 불가능에 가까워야 합니다.
- **눈사태 효과**: 입력의 한 비트만 달라져도 출력의 많은 비트가 예측하기 어렵게 바뀌어야 합니다.
- **원상 저항성**: 주어진 출력과 일치하는 입력 하나를 찾는 일도 충분히 어려워야 합니다.

“균등 분포”와 “충돌 저항성”은 서로 다른 요구입니다. 단순한 `key % 100`도 무작위 키에서는 출력이 고르게 보일 수 있지만, 마지막 두 자리가 같은 키가 항상 충돌한다는 규칙을 누구나 쉽게 이용할 수 있습니다. 해시 테이블 내부 분산에는 쓸 수 있어도 비밀번호 보호에는 사용할 수 없습니다.

사용 목적을 먼저 구분해야 합니다. 프로세스 내부의 임시 맵은 매우 빠른 비암호학적 해시가 적합할 수 있고, 외부에서 검증할 파일 지문이나 보안 토큰에는 표준 암호학적 해시가 필요합니다. 빠르다는 이유로 자체 제작 해시를 보안 기능에 재사용하면 안 됩니다.

## 해시 알고리즘 설계

강한 해시 설계는 전문적인 암호 분석과 광범위한 검증이 필요한 복잡한 작업입니다. 하지만 보안 요구가 없는 학습용 상황에서는 기본 아이디어를 이해하기 위한 단순 알고리즘을 만들 수 있습니다.

- **덧셈 해시**: 입력 문자열의 각 문자 코드를 모두 더합니다. 빠르지만 문자 순서를 구분하지 못합니다.
- **곱셈 해시**: 현재 해시 값에 상수를 곱한 뒤 다음 문자 코드를 누적합니다. 위치에 따라 가중치가 달라져 순서 정보를 반영합니다.
- **XOR 해시**: 각 입력 단위를 배타적 논리합으로 누적합니다. 계산은 빠르지만 교환 법칙 때문에 단순 형태는 충돌이 많습니다.
- **회전 해시**: 누적 전에 해시 값의 비트를 회전한 뒤 문자 코드를 합칩니다. 비트 위치를 섞어 단순 덧셈보다 분포를 개선합니다.

```python
# 잠긴 원문의 13개 언어 회전 해시 구현이 이 위치에 삽입됩니다.
```

예제 알고리즘은 마지막에 큰 소수 $1000000007$로 나머지를 취해 값의 범위를 제한합니다. 왜 합성수보다 소수를 선호할까요?

큰 소수는 다른 수와 공약수를 갖지 않으므로, 나머지 연산이 입력의 주기와 맞물려 반복 패턴을 만드는 위험을 줄입니다. 예를 들어 합성수 $9$를 법으로 사용하고 입력이 $3$의 배수만 따라온다면, 입력 간격도 $3$이고 해시는 $0$, $3$, $6$의 세 위치에만 모입니다.

$$
\begin{aligned}
\text{modulus} & = 9 \\
\text{key} & = \{0, 3, 6, 9, 12, 15, 18, 21, 24, 27, 30, 33, \ldots\} \\
\text{hash} & = \{0, 3, 6, 0, 3, 6, 0, 3, 6, 0, 3, 6, \ldots\}
\end{aligned}
$$

법을 소수 $13$으로 바꾸면 같은 입력 수열이 훨씬 다양한 나머지를 만듭니다.

$$
\begin{aligned}
\text{modulus} & = 13 \\
\text{key} & = \{0, 3, 6, 9, 12, 15, 18, 21, 24, 27, 30, 33, \ldots\} \\
\text{hash} & = \{0, 3, 6, 9, 12, 2, 5, 8, 11, 1, 4, 7, \ldots\}
\end{aligned}
$$

입력 키가 완전히 균등 무작위라면 소수와 합성수 모두 균등한 나머지를 만들 수 있습니다. 차이는 입력에 주기성이 있거나 특정 인수가 반복될 때 드러납니다. 충분히 큰 소수는 이런 입력 규칙과 법의 공통 주기가 생길 가능성을 낮춰 더 견고한 분포를 제공합니다.

소수를 쓴다고 해시가 자동으로 안전해지는 것은 아닙니다. 누적 규칙이 약하면 순서가 다른 문자열이나 비슷한 접두사가 여전히 쉽게 충돌합니다. 법 선택, 혼합 연산, 출력 비트 수를 함께 설계하고 실제 키 분포로 통계 검증해야 합니다.

## 대표적인 해시 알고리즘

덧셈이나 단순 XOR은 교환 법칙 때문에 같은 문자를 다른 순서로 배치한 문자열을 구분하지 못할 수 있습니다. 이러한 학습용 함수는 해시 설계 원리를 보여 주지만, 보안 목표와 실제 서비스의 공격 모델을 충족하지 못합니다.

실무에서는 공개적으로 분석된 표준 알고리즘을 사용합니다. MD5, SHA-1, SHA-2, SHA-3는 길이가 임의인 입력을 고정 길이 출력으로 변환합니다. 연구자는 성능과 구현을 개선하고, 암호 분석가는 충돌과 구조적 약점을 지속해서 찾습니다. 시간이 지나며 안전하다고 여겼던 알고리즘도 공격 가능성이 확인되어 용도가 바뀔 수 있습니다.

- **MD5**는 매우 빠르지만 실용적인 충돌 공격이 알려져 보안 서명에 사용해서는 안 됩니다. 우발적 파일 손상을 확인하는 비보안 체크섬에는 여전히 보이지만, 공격자가 파일을 만들 수 있는 상황에는 부적합합니다.
- **SHA-1**도 충돌이 실제로 시연되어 보안 용도에서 폐기 단계입니다.
- **SHA-2** 계열, 특히 SHA-256은 널리 배포되고 분석되었으며 현재 많은 보안 프로토콜, 서명, 콘텐츠 검증에 사용됩니다.
- **SHA-3**는 SHA-2와 다른 내부 구조를 사용하여 설계 다양성을 제공합니다. 구현 환경과 프로토콜 호환성에 따라 선택할 수 있습니다.

**표 · 대표적인 해시 알고리즘**

| 항목 | MD5 | SHA-1 | SHA-2 | SHA-3 |
| --- | --- | --- | --- | --- |
| 발표 연도 | 1992 | 1995 | 2002 | 2008 |
| 출력 길이 | 128비트 | 160비트 | 256/512비트 | 224/256/384/512비트 |
| 알려진 충돌 위험 | 높음 | 높음 | 매우 낮음 | 매우 낮음 |
| 보안 수준 | 낮음, 공격 성공 | 낮음, 공격 성공 | 높음 | 높음 |
| 대표 용도 | 비보안 무결성 확인 | 신규 보안 용도 금지 | 서명, 프로토콜, 거래 검증 | SHA-2의 대안 |

알고리즘 이름만으로 전체 시스템이 안전해지지는 않습니다. 비밀번호에는 범용 SHA를 한 번 계산하는 대신, 솔트와 느린 비밀번호 전용 파생 함수가 필요합니다. 무결성 값의 위조를 막으려면 단순 해시 대신 비밀키를 결합한 메시지 인증 코드나 디지털 서명을 사용해야 합니다.

출력 길이도 중요합니다. 충돌을 찾는 데 필요한 작업량은 일반적으로 출력 비트 수의 절반 지수 규모인 생일 경계와 관련됩니다. 따라서 장기간 보안이 필요한 시스템은 충분한 출력 길이와 현재 권고되는 알고리즘을 선택하고, 오래된 형식을 안전하게 교체할 수 있는 버전 전략을 가져야 합니다.

## 자료 구조에서의 해시 값

해시 테이블의 키는 정수, 실수, 문자열, 튜플, 사용자 정의 객체 등 여러 자료형이 될 수 있습니다. 언어 런타임은 각 형식에 맞는 기본 해시 함수를 제공하고, 해시 테이블은 그 결과로 버킷을 계산합니다.

- 정수와 불리언은 값 자체 또는 값에 가까운 단순 규칙을 사용할 수 있습니다.
- 실수는 부호, 지수, 가수 표현과 값의 동등성 규칙을 일관되게 반영해야 합니다. 양의 0과 음의 0, NaN 같은 경계 사례도 언어 계약에 포함됩니다.
- 문자열은 문자 순서와 전체 내용을 섞어야 하며, 일부 런타임은 실행마다 무작위 시드를 사용합니다.
- 튜플은 각 구성 요소의 해시를 순서대로 결합합니다. 구성 요소가 해시 가능해야 튜플도 안전한 키가 됩니다.
- 사용자 정의 객체는 기본적으로 객체 정체성이나 메모리 주소에서 해시를 만들 수 있고, 내용 기반 동등성을 정의했다면 그와 일치하는 내용 기반 해시도 함께 정의해야 합니다.

사용자 정의 객체가 가변 멤버를 가져도 정체성 기반 해시는 가능할 수 있습니다. 객체의 메모리상 정체성은 내용이 바뀌어도 유지되기 때문입니다. 반대로 두 객체의 내용이 같으면 같은 키로 간주하도록 `equals`를 재정의했다면, 같은 내용의 객체가 반드시 같은 해시를 내도록 `hash`도 함께 재정의해야 합니다. 동등한 두 키의 해시가 다르면 테이블이 서로 다른 버킷을 찾아 계약이 깨집니다.

실행할 때마다 문자열 해시가 달라지는 현상도 정상일 수 있습니다. Python 같은 런타임은 프로세스 시작 시 무작위 솔트를 섞어 공격자가 대량 충돌 키를 미리 준비하기 어렵게 만듭니다. 따라서 내장 해시는 프로세스 내부 자료 구조용이며, 영구 식별자나 네트워크 프로토콜 값이 필요하면 명세가 고정된 별도 알고리즘을 사용해야 합니다.

자료 구조용 해시의 핵심은 속도, 동등성 일관성, 현재 키 분포에 대한 균등성입니다. 암호학적 해시의 핵심은 공격자가 입력을 선택해도 역산과 충돌 생성이 어렵다는 점입니다. 이름은 같지만 목표와 비용 구조가 다르므로, 문제의 신뢰 경계를 먼저 판단한 뒤 알맞은 도구를 선택해야 합니다.

해시 구현을 검토할 때는 몇 가지 계약을 명시적으로 확인할 수 있습니다. 첫째, 동일한 실행과 동일한 키에서 결과가 결정적인가. 둘째, 동등하다고 판단하는 두 키가 반드시 같은 해시를 내는가. 셋째, 서로 다른 실제 키 표본에서 하위 비트와 상위 비트가 충분히 섞이는가. 넷째, 짧은 문자열·긴 문자열·공통 접두사·연속 정수처럼 현실적인 입력군에서 특정 버킷으로 치우치지 않는가. 이 검사는 암호학적 안전성을 증명하지는 않지만 자료 구조용 함수의 명백한 분포 결함을 빠르게 찾습니다.

벤치마크도 해시 계산 시간만 재면 충분하지 않습니다. 실제 해시 테이블에서는 버킷 인덱스 계산, 키 동등성 비교, 메모리 접근, 충돌 해결, 확장이 함께 비용을 만듭니다. 계산이 조금 더 비싸더라도 분포가 좋아 탐사 횟수를 크게 줄이는 함수가 전체 연산에서는 더 빠를 수 있습니다. 반대로 작은 정수처럼 이미 잘 분산된 키에 무거운 암호학적 함수를 쓰면 안전성 이득 없이 처리량만 줄어듭니다.

영구 데이터 형식에서는 알고리즘과 인코딩을 함께 고정해야 합니다. 같은 문자열도 문자 인코딩, 정규화, 바이트 순서가 다르면 다른 바이트열과 다른 해시가 됩니다. 파일이나 네트워크 메시지의 지문을 여러 시스템이 공유한다면 입력을 어떤 바이트로 직렬화하는지, 알고리즘 버전과 출력 표기를 어떻게 기록하는지까지 명세해야 재현 가능한 결과를 얻을 수 있습니다.

보안 알고리즘 선택은 최신 표준과 라이브러리 지침을 따라야 합니다. 직접 만든 혼합 함수는 겉보기에 출력이 무작위처럼 보여도 구조적 약점을 숨기고 있을 수 있습니다. 검증된 구현을 사용하고, 알고리즘을 하드코딩하지 말고 교체 가능한 형식으로 저장하며, 비교할 때는 시간 차이를 이용한 부채널까지 고려하는 것이 안전한 운영의 일부입니다.

요약하면 좋은 해시는 목적에 맞는 비용으로 입력 정보를 고르게 섞고, 동등성 계약과 실행 환경의 요구를 지킵니다. 해시 테이블에서는 빠른 분포가 우선이고, 보안 경계에서는 공격자가 선택한 입력에도 견디는 검증된 단방향 함수가 우선입니다. 두 상황을 같은 이름 때문에 혼동하지 않는 것이 올바른 설계의 출발점입니다.

입력 형식과 신뢰 경계를 문서화하면 이후 구현 교체와 보안 검토도 훨씬 명확해집니다.

테스트 벡터와 예상 출력도 함께 기록하면 여러 언어 구현의 일치 여부를 반복해서 검증할 수 있습니다.
