# 요약

### 핵심 복습

- 해시 테이블은 입력 키 `key`에 대응하는 값 `value`를 평균 $O(1)$ 시간에 찾을 수 있어 조회 중심 문제에 매우 효율적입니다.
- 기본 연산에는 키 조회, 키–값 쌍 추가, 기존 값 갱신, 키 삭제, 키·값 순회가 있습니다. 누락 키와 순회 순서의 계약은 언어마다 다를 수 있습니다.
- 해시 함수는 키를 배열 인덱스로 대응시킵니다. 저장과 조회가 같은 함수, 같은 동등성 규칙, 현재 용량을 사용해야 같은 버킷에 도달합니다.
- 서로 다른 키가 같은 인덱스를 얻는 현상이 해시 충돌입니다. 충돌은 원리적으로 피할 수 없으며, 올바른 구현은 충돌한 실제 키를 다시 비교하여 각각의 값을 보존합니다.
- 용량이 커지면 여러 키가 같은 버킷에 모일 확률이 낮아질 수 있습니다. 그러나 확장은 모든 쌍을 새 용량으로 재해싱해야 하므로 비용이 큽니다.
- 적재율은 원소 수를 버킷 수로 나눈 비율입니다. 충돌의 심각도를 추정하고 확장을 시작하는 임계값으로 자주 사용됩니다.
- 분리 연결법은 같은 버킷에 대응된 쌍을 연결 리스트나 동적 배열에 함께 저장합니다. 버킷이 지나치게 길어지면 레드-블랙 트리 같은 균형 트리로 바꾸어 최악의 탐색을 완화할 수 있습니다.
- 개방 주소법은 버킷 배열 안에서 다음 후보를 탐사합니다. 선형 탐사는 단순하고 캐시에 유리하지만 군집화가 생기며, 중간 원소를 단순 빈 칸으로 삭제할 수 없어 묘비 표식이 필요합니다.
- 제곱 탐사는 탐사 간격을 제곱으로 늘려 1차 군집화를 줄이고, 다중 해싱은 여러 해시 함수나 두 번째 해시 간격으로 후보를 분산합니다. 더 나은 분포 대신 계산 비용과 구현 복잡도가 늘어납니다.
- 언어별 구현 전략은 다릅니다. Java의 `HashMap`은 분리 연결법과 트리 전환을 사용하고, Python의 `dict`는 개방 주소 계열을 사용합니다. 사용자 코드는 내부 방식보다 공개 API 계약에 의존해야 합니다.
- 자료 구조용 해시에는 결정성, 높은 계산 효율, 현재 키 집합에 대한 균등 분포가 중요합니다. 암호학적 해시에는 단방향성, 충돌 저항성, 눈사태 효과가 추가로 필요합니다.
- 큰 소수를 법으로 사용하면 입력의 주기와 나머지 연산의 주기가 겹쳐 특정 출력에 몰리는 위험을 낮출 수 있습니다. 다만 소수 하나만으로 약한 혼합 함수가 안전해지는 것은 아닙니다.
- MD5와 SHA-1은 충돌 공격 때문에 새로운 보안 용도에 적합하지 않습니다. SHA-2와 SHA-3 같은 현재 표준은 검증된 라이브러리로 사용해야 하며, 비밀번호에는 솔트와 전용 파생 함수가 필요합니다.
- 언어는 숫자, 문자열, 튜플, 객체에 대한 내장 해시를 제공합니다. 일반적으로 키는 저장된 동안 해시와 동등성이 변하지 않아야 하므로 불변 객체가 적합합니다.

### 질문과 답변

**질문**: 해시 테이블의 시간 복잡도는 언제 $O(n)$으로 저하됩니까?

충돌이 매우 심해 모든 키가 한 버킷이나 긴 탐사 군집에 모이면 $O(n)$까지 저하될 수 있습니다. 해시 함수가 고르게 분산하고, 용량과 적재율이 적절하며, 충돌 해결 구조가 정상이라면 평균 연산은 $O(1)$입니다. 따라서 표준 라이브러리의 내장 맵은 일반적으로 평균 $O(1)$로 분석하지만, 공격적 입력과 최악의 분포 가능성은 별도로 고려합니다.

**질문**: 충돌을 없애기 위해 해시 함수 $f(x) = x$를 사용하면 되지 않습니까?

$f(x) = x$에서는 각 정수가 고유 인덱스와 대응하므로 사실상 거대한 직접 주소 배열입니다. 그러나 입력 공간은 실제 배열 길이보다 훨씬 큰 경우가 많고, 키가 문자열처럼 정수 인덱스가 아닐 수도 있습니다. 해시 테이블의 목적은 큰 상태 공간을 제한된 버킷 공간으로 압축하면서 평균 $O(1)$ 조회를 제공하는 것입니다. 압축이 있는 한 충돌 가능성도 함께 존재합니다.

**질문**: 해시 테이블이 배열, 연결 리스트 또는 트리로 구현되는데도 왜 더 빠를 수 있습니까?

해시 테이블은 추가 빈 공간과 해시 계산을 사용하여 목표가 있을 가능성이 높은 작은 위치로 곧바로 이동합니다. 순서 없는 배열이나 리스트를 처음부터 훑는 것보다 빠르지만 메모리 효율은 낮습니다. 같은 기능을 배열만으로 같은 복잡도에 구현할 수 있다면 해시 계산의 상수 비용 때문에 배열이 더 빠를 수 있습니다. 또한 분리 연결 버킷이 길어지면 내부 탐색은 여전히 $O(n)$으로 악화될 수 있습니다.

**질문**: 다중 해싱도 원소를 직접 삭제할 수 없습니까? 삭제 표시 공간은 다시 쓸 수 있습니까?

다중 해싱도 개방 주소법이므로 탐사 열 중간을 미사용 빈 칸으로 바꾸면 뒤의 원소가 끊깁니다. 삭제 표식을 남겨 조회는 계속 지나가게 해야 합니다. 새 원소를 삽입할 때는 그 표식 위치를 재사용할 수 있으므로 탐사 연속성과 공간 이용을 함께 유지할 수 있습니다.

**질문**: 선형 탐사의 조회 과정에서도 왜 충돌이 발생했다고 말합니까?

해시 함수가 가리킨 버킷의 키가 조회 키와 다르면 두 키가 같은 시작 인덱스를 얻은 것입니다. 이것이 충돌입니다. 조회는 저장 때 사용한 간격으로 계속 이동하여 같은 키를 찾거나, 한 번도 사용되지 않은 빈 위치에서 실패를 확정합니다.

**질문**: 해시 테이블 확장은 왜 충돌을 완화합니까?

버킷 인덱스의 마지막 계산은 보통 배열 길이 $n$으로 나머지를 취합니다. 확장하면 $n$이 바뀌고 각 키의 인덱스도 달라질 수 있습니다. 이전에 같은 버킷에 있던 키들이 새 용량에서는 여러 버킷으로 흩어지므로 충돌이 줄어듭니다. 이 때문에 확장 시 단순 복사가 아니라 모든 키의 재해싱이 필요합니다.

**질문**: 빠른 접근이 목표라면 배열을 직접 쓰면 되지 않습니까?

키가 작고 연속된 정수 범위라면 배열이 가장 단순하고 빠른 선택입니다. 하지만 키가 문자열이나 희소한 큰 정수라면 직접 주소 배열은 만들 수 없거나 대부분의 공간을 낭비합니다. 해시 함수가 그런 키를 제한된 인덱스로 바꾸고 버킷 배열에 저장한 구조가 바로 해시 테이블입니다.

해시 테이블을 설계하거나 선택할 때는 키 분포, 예상 원소 수, 삭제 빈도, 순서 요구를 함께 살펴야 합니다. 존재 여부와 정확한 키 조회가 중심이면 매우 좋은 선택이지만, 범위 검색이나 정렬된 순회가 필요하면 균형 트리나 정렬 배열이 더 적합할 수 있습니다. 평균 복잡도 하나만 보고 결정하지 말고, 확장 순간의 지연과 추가 메모리도 평가해야 합니다.

직접 구현을 검증할 때는 충돌 키, 없는 키, 같은 키의 갱신, 중간 삭제, 원형 탐사, 확장 뒤 재조회까지 시험해야 합니다. 해시와 동등성은 하나의 계약이므로 동등한 키는 같은 해시를 내야 하고, 저장된 키의 해시는 테이블 안에 있는 동안 변하지 않아야 합니다. 이 두 불변식이 깨지면 데이터가 실제로 남아 있어도 조회할 수 없습니다.

보안 용도의 해시는 별도 문제입니다. 표준 암호 라이브러리를 사용하고, 입력 직렬화와 알고리즘 버전을 기록하며, 오래된 알고리즘을 교체할 수 있어야 합니다. 자료 구조용 내장 해시 숫자를 파일 식별자나 인증 값으로 재사용해서는 안 됩니다.
