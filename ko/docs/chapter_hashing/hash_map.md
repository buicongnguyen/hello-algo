# 해시 테이블

<u>해시 테이블</u> 또는 <u>해시 맵</u>은 키 `key`에서 값 `value`로의 대응 관계를 저장하는 자료 구조입니다. 키가 주어지면 평균 상수 시간에 대응 값을 찾을 수 있다는 점이 가장 큰 장점입니다.

예를 들어 여러 학생에게 이름과 학번이 있을 때 “학번으로 이름 찾기”를 반복한다면, 학번을 키로 하고 이름을 값으로 하는 해시 테이블이 적합합니다.

![해시 테이블의 추상 표현](hash_map.assets/hash_table_lookup.png)

배열과 연결 리스트도 조회 기능을 만들 수 있지만, 순서가 없는 상태에서의 성능은 다릅니다.

- **추가**: 배열이나 연결 리스트의 끝에 넣으면 $O(1)$입니다.
- **조회**: 목표를 찾을 때까지 순차 탐색하므로 $O(n)$입니다.
- **삭제**: 먼저 목표를 찾은 뒤 제거해야 하므로 $O(n)$입니다.

**표 · 원소 연산의 효율 비교**

| 연산 | 배열 | 연결 리스트 | 해시 테이블 |
| --- | --- | --- | --- |
| 원소 찾기 | $O(n)$ | $O(n)$ | $O(1)$ |
| 원소 추가 | $O(1)$ | $O(1)$ | $O(1)$ |
| 원소 삭제 | $O(n)$ | $O(n)$ | $O(1)$ |

따라서 해시 테이블에서 삽입, 삭제, 조회, 갱신은 평균적으로 모두 $O(1)$이며, 많은 조회를 처리할 때 매우 효율적입니다. 다만 이 결론은 충돌이 적절히 제어된 평균 상황을 전제로 합니다.

배열에서는 위치 자체가 식별자이지만, 해시 테이블에서는 키와 저장 위치가 분리됩니다. 문자열, 학번, 객체처럼 배열 인덱스로 바로 쓸 수 없는 키도 해시 함수가 정수 위치로 바꾸어 줍니다. 이 간접 계층 덕분에 키의 형태와 저장 배열의 크기를 독립적으로 설계할 수 있습니다.

또한 해시 테이블은 “키가 같은가”와 “해시 값이 같은가”를 구분해야 합니다. 해시 값이 같아도 키는 다를 수 있으므로, 후보 버킷에 도착한 뒤에는 실제 키 동등성 검사를 거쳐야 합니다. 기존 키와 같으면 값을 갱신하고, 다른 키라면 충돌 해결 규칙에 따라 함께 보관합니다. 이 규칙을 빠뜨리면 우연히 같은 버킷을 받은 서로 다른 데이터가 덮어써집니다.

## 해시 테이블의 기본 연산

주요 연산은 초기화, 키–값 쌍 추가, 키 조회, 키 삭제입니다. 언어마다 `dict`, `Map`, `HashMap`, `unordered_map`처럼 이름과 문법은 다르지만 논리적 동작은 같습니다.

조회는 키가 반드시 존재한다고 가정하는 연산과, 없을 때 기본값 또는 실패 상태를 반환하는 연산으로 나뉩니다. 실제 프로그램에서는 누락된 키가 정상 상황인지 오류인지 먼저 결정해야 합니다. 예를 들어 학생 학번 조회에서 등록되지 않은 학번은 “찾지 못함”으로 처리할 수 있지만, 내부 설정 값이 없으면 즉시 오류를 내는 편이 안전할 수 있습니다.

추가는 새 키를 만드는 경우와 기존 키의 값을 갱신하는 경우를 모두 포함합니다. 삭제 역시 키가 없을 때 조용히 무시할지, 실패를 보고할지 언어별 API가 다릅니다. 따라서 다른 언어의 코드를 옮길 때는 문법만 바꾸지 말고 누락 키에 대한 계약도 확인해야 합니다.

## 단순한 해시 테이블 구현

가장 단순한 형태는 배열 하나로 해시 테이블을 구현하는 것입니다. 배열의 각 빈 칸을 <u>버킷</u>이라고 하며, 한 버킷은 하나의 키–값 쌍을 저장합니다. 조회는 키에 맞는 버킷을 계산하고 그곳의 값을 읽는 과정입니다.

해시 함수는 큰 입력 공간을 작은 출력 공간으로 대응시킵니다. 해시 테이블에서는 모든 가능한 키가 입력 공간이고, 배열의 인덱스가 출력 공간입니다. 키가 주어졌을 때 버킷 인덱스는 두 단계로 계산합니다.

1. 해시 알고리즘 `hash()`로 정수 해시 값을 계산합니다.
2. 그 값을 버킷 수 `capacity`로 나눈 나머지를 취합니다.

```shell
index = hash(key) % capacity
```

예를 들어 배열 길이가 100이고 `hash(key) = key`라면, 학생 학번의 마지막 두 자리가 버킷을 결정합니다.

단순 구현에서 `get`은 계산된 버킷을 읽고 키가 일치하는지 확인합니다. `put`은 빈 버킷이면 새 쌍을 저장하고, 같은 키가 있으면 값을 교체합니다. `remove`는 목표 쌍을 찾아 비웁니다. 각 연산이 같은 `hash()`와 같은 용량을 사용해야만 저장할 때와 찾을 때의 경로가 일치합니다.

해시 함수는 키가 변하지 않는 동안 같은 결과를 내야 합니다. 저장 후 키의 내용이 바뀌어 해시 값까지 달라지면, 원소는 예전 버킷에 남아 있지만 조회는 새 버킷으로 향해 찾지 못합니다. 그래서 대부분의 언어는 문자열·숫자·튜플 같은 불변 값을 키로 권장하고, 가변 객체를 키로 쓸 때는 해시와 동등성 규칙을 매우 신중하게 정의하도록 요구합니다.

## 해시 충돌과 확장

해시 함수의 입력 공간은 보통 버킷 배열보다 훨씬 큽니다. 따라서 서로 다른 입력이 같은 출력으로 대응되는 경우를 원리적으로 완전히 없앨 수 없습니다.

앞의 함수에서 마지막 두 자리가 같은 두 학번은 같은 인덱스를 만듭니다.

```shell
12836 % 100 = 36
20336 % 100 = 36
```

두 키가 같은 버킷을 가리키는 현상을 <u>해시 충돌</u>이라고 합니다. 충돌을 처리하지 않는 단순 구현에서는 한 학생의 이름이 다른 학생의 이름을 덮어써 잘못된 결과를 만들 수 있습니다.

![해시 충돌의 예](hash_map.assets/hash_collision.png)

버킷 수를 늘리면 여러 키가 같은 위치에 모일 확률이 줄어듭니다. 그래서 해시 테이블은 필요할 때 더 큰 배열을 만들고 모든 키–값 쌍을 다시 배치합니다.

![해시 테이블 확장과 재해싱](hash_map.assets/hash_table_reshash.png)

확장은 배열 확장처럼 기존 데이터를 옮겨야 할 뿐 아니라, `capacity`가 바뀌었으므로 각 키의 인덱스를 다시 계산해야 합니다. 한 번의 확장은 선형 시간이 걸릴 수 있어 비용이 크므로, 구현체는 여유 용량을 두고 확장 빈도를 제한합니다.

<u>적재율</u>은 원소 수를 버킷 수로 나눈 값입니다. 충돌의 심각도를 간접적으로 나타내며, 보통 확장을 시작하는 임계값으로 쓰입니다. 예를 들어 Java 구현은 적재율이 약 0.75를 넘으면 대개 용량을 두 배로 늘립니다.

확장할 때 기존 배열을 그대로 더 큰 배열 앞부분에 복사할 수는 없습니다. 버킷 인덱스 계산에 용량이 포함되므로, 용량이 달라지면 같은 키도 새 위치를 가질 수 있습니다. 따라서 모든 키를 꺼내 새 용량으로 인덱스를 다시 계산하는 <u>재해싱</u>이 필요합니다. 이 작업은 한 번에는 무겁지만, 용량을 배수로 늘리면 여러 삽입에 비용이 분산되어 평균 연산 비용을 낮게 유지할 수 있습니다.

적재율을 지나치게 낮게 유지하면 빈 버킷이 많아 메모리를 낭비하고, 지나치게 높이면 충돌과 탐사 길이가 늘어납니다. 적절한 임계값은 충돌 해결 방식, 키 분포, 메모리 제한에 따라 달라집니다. 라이브러리의 기본값은 일반적인 상황에 맞춘 절충안이며, 특수한 대규모 작업에서는 예상 원소 수로 초기 용량을 예약하면 반복 확장을 줄일 수 있습니다.

좋은 해시 함수, 적절한 적재율, 올바른 충돌 해결 전략이 함께 갖추어져야 평균 상수 시간이라는 장점을 안정적으로 유지할 수 있습니다.

해시 테이블을 문제 풀이에 사용할 때는 먼저 키의 의미를 명확히 정하는 것이 좋습니다. 빈도표에서는 관찰한 값이 키이고 출현 횟수가 값이며, 중복 제거에서는 값 자체가 키이고 값 부분은 생략할 수 있습니다. 두 값의 대응 관계를 저장할 때는 어느 방향으로 조회할지에 따라 키와 값을 정합니다. 양방향 조회가 모두 잦다면 하나의 테이블을 억지로 순회하기보다 반대 방향 테이블을 함께 유지하는 편이 낫습니다.

성능을 판단할 때 평균 비용과 한 번의 지연 시간을 구분해야 합니다. 확장이 드물게 일어나 평균 비용은 낮아도, 실시간 처리에서는 그 한 번의 재해싱이 눈에 띄는 지연을 만들 수 있습니다. 예상 크기를 알고 있다면 초기 용량을 예약하고, 입력 키가 공격자가 제어할 수 있다면 충돌을 의도적으로 집중시키는 공격에도 대비해야 합니다.

마지막으로 해시 테이블은 정렬된 탐색이나 범위 질의에는 적합하지 않습니다. “특정 키가 있는가”에는 강하지만 “이 키보다 작은 모든 원소”에는 순서를 보존하는 트리나 정렬 배열이 더 자연스럽습니다. 자료 구조를 선택할 때는 단일 연산의 속도뿐 아니라 필요한 질의 종류, 순서 보장, 메모리 사용량을 함께 비교해야 합니다.
