# 요약

### 핵심 내용 복습

- 버블 정렬은 이웃 원소를 교환하여 순서를 만듭니다. 교환이 없었던 라운드를 감지하는 플래그를 추가하면 최선의 경우 $O(n)$에 종료할 수 있습니다.
- 삽입 정렬은 매 라운드에 정렬되지 않은 원소 하나를 선택하여 정렬된 접두사의 올바른 위치에 삽입합니다. $O(n^2)$이지만 연산이 단순하고 기존 순서를 활용하므로 짧은 구간에서 매우 유용합니다.
- 퀵 정렬은 피벗 분할을 바탕으로 합니다. 나쁜 피벗을 계속 선택하면 $O(n^2)$으로 악화될 수 있습니다. 세 값의 중앙값이나 무작위 피벗은 악화 확률을 줄이고, 짧은 부분에만 재귀 호출하면 스택을 $O(\log n)$으로 제한합니다.
- 병합 정렬은 분할과 병합 단계로 이루어져 분할 정복을 명확히 보여 줍니다. 배열 버전은 $O(n)$ 보조 메모리가 필요하지만, 연결 리스트 버전은 노드 연결을 바꾸어 정렬 공간을 $O(1)$까지 최적화할 수 있습니다.
- 버킷 정렬은 데이터를 여러 버킷에 분배하고 각 버킷을 정렬한 뒤 결과를 합칩니다. 매우 큰 데이터에 활용할 수 있지만 원소가 비교적 고르게 분배되어야 효율적입니다.
- 계수 정렬은 각 정수 값을 하나의 버킷처럼 보고 출현 빈도로 순서를 만듭니다. 원소 수는 크고 값 범위는 작을 때 적합하며, 데이터가 순서를 보존하는 음이 아닌 정수로 매핑될 수 있어야 합니다.
- 기수 정렬은 낮은 자릿수부터 높은 자릿수까지 안정 정렬을 반복합니다. 데이터가 유한하고 너무 크지 않은 자릿수 표현을 가져야 합니다.
- 모든 데이터에서 동시에 빠르고, 안정적이고, 제자리이고, 적응형이며, 범용적인 알고리즘은 없습니다. 실제 선택은 크기, 메모리, 키 분포, 안정성 요구, 입력의 기존 순서를 기준으로 해야 합니다.
- 아래 그림은 주요 알고리즘의 효율, 안정성, 제자리 속성, 적응성을 비교합니다.

![정렬 알고리즘 비교](summary.assets/sorting_algorithms_comparison.png)

비교 기반 정렬에서는 일반적으로 `O(n log n)`이 최적 한계이지만, 계수·버킷·기수 정렬은 키의 추가 구조를 이용해 이 한계를 피합니다. 그 대가로 값 범위, 분포, 자릿수 같은 적용 조건과 추가 메모리가 필요합니다.

세 가지 단순 정렬도 역할이 다릅니다. 선택 정렬은 교환 수가 적지만 비교 수를 줄이지 못하고 불안정합니다. 버블 정렬은 안정적이고 조기 종료가 가능하지만 교환이 많습니다. 삽입 정렬은 이동 비용이 낮고 거의 정렬된 작은 구간에 강해 혼합 정렬의 마무리 단계로 자주 사용됩니다.

분할 정복 계열에서도 선택 기준이 다릅니다. 퀵 정렬은 평균적으로 빠르고 캐시 친화적이며 제자리이지만 피벗에 따라 최악 시간이 나빠질 수 있습니다. 병합 정렬은 안정적이고 최악 시간도 일정하지만 배열 보조 공간이 필요합니다. 힙 정렬은 최악 `O(n log n)`과 `O(1)` 보조 공간을 함께 보장하지만 캐시 지역성과 안정성에서 불리합니다.

### 질문과 답변

**질문**: 정렬 알고리즘의 안정성은 언제 필요한가요?

여러 기준으로 단계적으로 정렬할 때 한 객체의 여러 속성을 차례로 처리합니다. 학생 목록이 이름순 `(A, 180) (B, 185) (C, 170) (D, 170)`이고 이후 키순으로 정렬한다고 합시다. 불안정 정렬은 `(D, 170) (C, 170) (A, 180) (B, 185)`를 만들 수 있습니다. 키가 같은 C와 D가 뒤집혀 앞 단계의 이름순이 사라집니다. 안정 정렬은 C를 D 앞에 유지합니다.

안정성을 이용하면 가장 낮은 우선순위 기준부터 높은 우선순위 기준까지 차례로 정렬하여 다단계 순서를 만들 수 있습니다. 각 단계가 같은 키의 기존 순서를 보존하기 때문에 앞 단계의 결과가 다음 단계에서 유지됩니다.

**질문**: 왼쪽 원소를 피벗으로 쓰는 분할에서 “오른쪽에서 왼쪽 찾기”와 “왼쪽에서 오른쪽 찾기”의 순서를 바꿀 수 있나요?

바꿀 수 없습니다. `partition()`의 마지막은 `nums[left]`와 `nums[i]`를 교환하므로, 교환 직전에 `i` 위치의 값이 피벗보다 크지 않음을 보장해야 합니다. 왼쪽부터 먼저 찾다가 피벗보다 큰 원소를 만나지 못하면 `i == j`로 끝난 위치가 여전히 `nums[left]`보다 클 수 있습니다. 두 값을 교환하면 큰 원소가 피벗 왼쪽에 들어가 분할 불변식을 깨뜨립니다.

`[0, 0, 0, 0, 1]`에서 왼쪽 탐색부터 하면 `[1, 0, 0, 0, 0]`이 될 수 있어 명백히 잘못됩니다. 피벗이 오른쪽 원소라면 논리가 대칭이므로 왼쪽에서 오른쪽 탐색을 먼저 수행해야 합니다.

중요한 것은 코드 한 줄의 순서 자체가 아니라 마지막 교환 전에 경계 원소가 어느 관계를 만족해야 하는지입니다. 피벗을 어디에 저장하고 어떤 비교 연산을 쓰는지에 따라 올바른 탐색 순서도 달라집니다.

**질문**: 짧은 부분에만 재귀 호출하면 깊이가 $\log n$을 넘지 않는 이유는 무엇인가요?

깊이는 아직 반환되지 않은 호출 수입니다. 분할 뒤 짧은 부분의 길이는 현재 구간의 절반 이하입니다. 최악에도 정확히 절반씩 이어진다면 계속 나눌 수 있는 횟수는 $\log n$입니다.

최적화하지 않은 버전은 더 긴 부분을 크기 $n$, $n - 1$, $\dots$, $2$, $1$로 연속 재귀 호출하여 깊이 $n$에 이를 수 있습니다. 긴 가지를 반복문으로 바꾸면 이런 호출 누적이 사라집니다.

이 최적화는 분할 품질이 나빠도 스택을 보호합니다. 실행 시간 자체는 여전히 편향된 분할의 영향을 받을 수 있으므로, 좋은 피벗 선택과 함께 적용해야 시간과 공간 모두 안정됩니다.

**질문**: 모든 원소가 같을 때 퀵 정렬은 $O(n^2)$이 되나요?

일반적인 양방향 분할에서는 그럴 수 있습니다. 해결책은 피벗보다 작은 구간, 같은 구간, 큰 구간으로 나누는 **삼방향 분할**입니다. 작은 부분과 큰 부분에만 재귀 호출합니다. 모든 원소가 같다면 한 번의 분할로 끝나 $O(n^2)$ 퇴화를 피합니다.

삼방향 분할은 중복 키가 많은 데이터에서 특히 효과적입니다. 같은 구간은 이미 최종 위치 관계를 만족하므로 다시 처리하지 않아도 됩니다.

**질문**: 버킷 정렬의 최악 시간이 $O(n^2)$인 이유는 무엇인가요?

모든 원소가 같은 버킷에 들어가면 문제를 나눈 이점이 사라집니다. 그 버킷 안에서 사용하는 정렬이 제곱 시간이라면 전체 버킷 정렬도 $O(n^2)$이 됩니다.

따라서 버킷 수만 늘리는 것보다 입력 분포에 맞는 경계를 고르는 것이 중요합니다. 표본이나 알려진 확률 분포로 경계를 조정하고 과도하게 큰 버킷을 재분할하면 최악에 가까운 불균형을 줄일 수 있습니다.
