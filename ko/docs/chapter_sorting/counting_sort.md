# 계수 정렬

<u>계수 정렬</u>은 각 값의 출현 횟수를 세어 순서를 만들며 주로 정수 배열에 적용합니다. 원소끼리 직접 비교하지 않고 값 자체를 보조 배열의 인덱스로 사용합니다.

## 단순 구현

길이 $n$인 배열 `nums`의 모든 원소가 음이 아닌 정수라고 가정합니다.

1. 배열을 순회하여 최댓값 $m$을 찾고 길이 $m + 1$인 보조 배열 `counter`를 만듭니다.
2. `counter`에 빈도를 기록합니다. `counter[num]`은 `num`의 출현 횟수이며, `num`을 만날 때마다 해당 칸을 $1$ 증가시킵니다.
3. `counter`의 인덱스는 이미 오름차순입니다. 계수 배열을 순회하며 각 인덱스를 출현 횟수만큼 `nums`에 다시 쓰면 자연스럽게 정렬됩니다.

!!! note "계수 정렬과 버킷 정렬의 관계"

## 완전한 구현

입력 원소가 객체라면 위 3단계처럼 인덱스 값만 다시 쓰는 방법은 키만 정렬할 뿐 원래 객체의 순서를 만들지 못합니다. 상품을 가격으로 정렬할 때는 가격 목록만이 아니라 각 상품 레코드 전체를 보존해야 합니다.

이를 해결하려면 먼저 `counter`의 누적 합을 계산합니다. 인덱스 `i`의 누적 합은 `0`부터 `i`까지 모든 계수의 합입니다.

$$
\text{prefix}[i] = \sum_{j=0}^i \text{counter}[j]
$$

`prefix[num] - 1`은 결과 배열 `res`에서 값 `num`이 마지막으로 나타날 인덱스입니다. 이 위치 정보를 이용하여 `nums`를 오른쪽에서 왼쪽으로 순회하고 각 `num`에 대해:

1. `num`을 `res[prefix[num] - 1]`에 놓습니다.
2. `prefix[num]`을 $1$ 줄여 같은 값의 다음 원소가 바로 앞 칸에 들어가도록 합니다.

모든 원소를 처리하면 `res`가 정렬 결과를 담습니다. 마지막에 `res`를 `nums`로 복사합니다. 객체를 정렬할 때는 `num` 대신 객체 전체를 결과 위치에 기록하고, 계수와 누적 합에는 정렬 키만 사용합니다.

## 알고리즘 특성

- **시간 복잡도 $O(n + m)$, 비적응형**: `nums`와 `counter`를 각각 선형 순회합니다. $n \gg m$이면 비용은 $O(n)$에 가까워집니다. 입력의 기존 순서는 기본 구현의 순회량을 줄이지 않습니다.
- **공간 복잡도 $O(n + m)$, 비제자리 정렬**: 길이 $n$의 `res`와 크기가 $m$에 비례하는 `counter`가 필요합니다.
- **안정 정렬**: `nums`를 오른쪽에서 왼쪽으로 순회하면 같은 값의 원소들이 `res`에 원래 상대적 순서로 들어갑니다. 정방향으로 순회해도 값은 정렬되지만 객체의 상대 순서가 뒤집혀 안정성을 잃을 수 있습니다.

오른쪽에서 왼쪽으로 배치하는 이유를 예로 확인할 수 있습니다. 같은 키를 가진 두 객체 A, B가 입력에서 A 뒤에 B 순서로 있다면 B를 먼저 결과 구간의 마지막 칸에 놓고, A를 그 앞 칸에 놓습니다. 최종 결과에서도 A가 B보다 앞에 남습니다.

## 제한

**계수 정렬은 직접적으로 음이 아닌 정수에만 적용됩니다.** 다른 데이터에는 순서를 바꾸지 않는 방식으로 음이 아닌 정수에 매핑해야 합니다. 음수가 있다면 모든 값에 같은 상수를 더해 최솟값을 0으로 옮긴 뒤 정렬하고, 필요하다면 결과에서 다시 상수를 뺄 수 있습니다.

문자나 범주형 키도 작고 연속적인 정수 코드로 변환할 수 있다면 적용 가능합니다. 하지만 실수처럼 가능한 값이 매우 많거나 비교 기준을 정수 구간으로 보존하기 어려운 데이터에는 적합하지 않습니다.

원소 수는 크지만 값의 범위가 작을 때 가장 효과적입니다. $m$이 지나치게 크면 계수 배열이 많은 메모리를 사용합니다. $n \ll m$이면 `counter`를 한 번 순회하는 비용만 $O(m)$이고, 오히려 $O(n \log n)$ 비교 정렬보다 느릴 수 있습니다.

따라서 계수 정렬을 선택하기 전에 입력 크기뿐 아니라 `최댓값 - 최솟값`으로 나타나는 실제 키 범위를 확인해야 합니다. 희소한 넓은 범위라면 해시 기반 계수나 다른 정렬을 고려하는 편이 낫습니다.
