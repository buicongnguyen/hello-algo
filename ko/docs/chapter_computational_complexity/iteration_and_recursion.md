# 반복과 재귀

알고리즘에서는 같은 작업을 여러 번 수행하는 일이 매우 흔하며, 반복 횟수는 복잡도와 직접 연결됩니다. 시간 복잡도와 공간 복잡도를 살펴보기 전에 반복 작업을 표현하는 두 가지 기본 제어 구조인 반복과 재귀를 이해해야 합니다.

## 반복

## 재귀

<u>재귀</u>는 함수가 자기 자신을 호출하여 문제를 푸는 알고리즘 전략입니다. 실행 과정은 두 단계로 나뉩니다.

1. **하강**: 더 작거나 단순한 매개변수로 자기 자신을 계속 호출하다가 종료 조건에 도달합니다.
2. **상승**: 가장 깊은 호출이 종료된 뒤 각 호출이 차례로 반환되면서 단계별 결과를 결합합니다.

재귀 코드는 보통 세 요소로 구성됩니다.

1. **종료 조건**: 하강을 멈추고 상승으로 전환할 시점을 결정합니다.
2. **재귀 호출**: 현재 문제를 같은 형태의 더 작은 문제로 바꿉니다.
3. **반환값**: 현재 단계의 결과를 이전 호출 단계에 전달합니다.

반복과 재귀는 같은 계산 결과를 만들 수 있지만 문제를 바라보는 관점이 다릅니다.

- **반복**은 아래에서 위로 풉니다. 가장 기본적인 단계부터 시작해 작업을 누적하며 전체 결과에 도달합니다.
- **재귀**는 위에서 아래로 풉니다. 원래 문제를 같은 형태의 더 작은 하위 문제로 분해하고, 해답을 이미 아는 기본 사례까지 내려갑니다.

합산 문제를 $f(n) = 1 + 2 + \dots + n$이라고 합시다.

- 반복은 $1$부터 $n$까지 이동하며 각 값을 누적해 $f(n)$을 얻습니다.
- 재귀는 $f(n) = n + f(n-1)$로 분해하고 기본 사례 $f(1) = 1$에서 멈춥니다.

### 호출 스택

재귀 함수가 자신을 호출할 때마다 시스템은 지역 변수, 매개변수, 반환 주소 등의 문맥을 보관할 새 스택 프레임을 만듭니다. 이 프레임은 해당 호출이 반환되기 전까지 해제되지 않습니다.

- 여러 호출의 문맥이 동시에 쌓이므로 **재귀는 일반적으로 반복보다 더 많은 메모리를 사용합니다.**
- 함수 호출과 반환 자체에도 비용이 있으므로 **재귀는 보통 단순 루프보다 시간 오버헤드가 큽니다.**

종료 조건에 도달하기 전에는 반환되지 않은 함수가 $n$개 동시에 존재할 수 있고, 이때 **재귀 깊이는 $n$**입니다.

![재귀 호출 깊이](iteration_and_recursion.assets/recursion_sum_depth.png)

프로그래밍 언어는 허용하는 재귀 깊이에 제한을 두는 경우가 많습니다. 입력이 지나치게 크면 호출 스택이 소진되어 스택 오버플로가 발생할 수 있습니다.

호출 스택은 재귀의 진행 순서를 자동으로 기억해 준다는 장점도 있습니다. 각 프레임은 현재 하위 문제의 상태와 하위 호출이 끝난 뒤 돌아갈 위치를 보존합니다. 반복으로 같은 동작을 구현하려면 이 상태를 명시적인 자료구조와 제어 변수로 직접 관리해야 하므로 코드가 더 길어질 수 있습니다.

### 꼬리 재귀

- 일반 재귀는 하위 호출이 반환된 뒤 남은 연산을 수행해야 하므로 이전 호출의 문맥을 보존합니다.

### 재귀 트리

분할 정복 문제에서는 재귀가 반복보다 문제 구조를 더 직접적으로 표현하는 경우가 많습니다. 피보나치 수열을 예로 살펴봅시다.

$n$번째 피보나치 수를 $f(n)$이라고 하면 다음 두 관계를 얻습니다.

재귀는 “문제를 더 작은 하위 문제로 분해한다”는 사고를 코드 구조로 표현합니다.

- 탐색, 정렬, 백트래킹, 분할 정복, 동적 계획법 등 많은 알고리즘 전략이 이 사고방식을 직접 또는 간접적으로 사용합니다.
- 연결 리스트, 트리, 그래프처럼 부분 구조가 전체와 비슷한 자료구조는 재귀로 자연스럽게 처리할 수 있습니다.

다만 재귀 트리의 모양은 곧 실행 비용을 보여 줍니다. 서로 다른 가지가 같은 하위 문제를 반복 계산한다면 호출 수가 매우 빠르게 증가합니다. 이때는 이미 계산한 결과를 저장하는 메모이제이션이나 아래에서 위로 값을 채우는 동적 계획법으로 중복을 제거할 수 있습니다.

## 반복과 재귀 비교

두 방식의 구현, 성능, 적용 대상을 정리하면 다음과 같습니다.

표: 반복과 재귀의 특성 비교

| 항목 | 반복 | 재귀 |
| --- | --- | --- |
| 구현 | 루프 구조 | 함수가 자기 자신을 호출 |
| 시간 효율 | 일반적으로 호출 오버헤드가 없어 더 효율적 | 각 함수 호출과 반환에 비용 발생 |
| 메모리 사용 | 보통 고정된 양의 임시 공간 사용 | 반환되지 않은 호출의 스택 프레임이 누적 |
| 적합한 문제 | 단순 반복 작업을 직관적으로 표현 | 트리, 그래프, 분할 정복, 백트래킹처럼 하위 문제 분해가 자연스러운 문제 |

!!! tip

    다음 설명이 어렵다면 “스택” 장을 읽은 뒤 다시 살펴보아도 좋습니다.

재귀 합산에서는 먼저 호출된 함수가 가장 나중에 덧셈을 끝냅니다. 이는 스택의 “후입선출” 원리와 같습니다. “호출 스택”과 “스택 프레임”이라는 용어도 이 관계를 직접 보여 줍니다.

반복은 현재 상태가 소수의 변수에 모여 있어 실행 흐름을 앞에서 뒤로 추적하기 쉽습니다. 재귀는 각 호출의 상태가 서로 다른 프레임에 분산되지만 문제의 계층 구조를 그대로 표현합니다. 디버깅할 때는 호출 깊이, 매개변수, 종료 조건을 함께 기록하면 어느 단계에서 잘못된 상태가 생겼는지 찾기 쉽습니다.

1. **하강**: 함수 호출 시 시스템이 지역 변수, 매개변수와 반환 주소를 저장할 새 프레임을 호출 스택 위에 올립니다.
2. **상승**: 함수가 끝나면 해당 프레임을 제거하고 이전 함수의 실행 문맥을 복원합니다.

따라서 명시적인 스택으로 호출 스택의 행동을 흉내 내면 재귀를 반복 형태로 바꿀 수 있습니다.


결국 **선택 기준은 문제의 구조**입니다. 단순한 누적은 반복이 명확하고, 동일한 형태의 하위 문제로 자연스럽게 나뉘는 작업은 재귀가 의도를 더 잘 표현합니다.

실무에서는 입력의 최대 크기와 사용하는 언어의 실행 특성도 함께 고려합니다. 재귀 표현이 훨씬 명확하더라도 깊이가 제한을 넘을 수 있다면 명시적 스택으로 바꾸거나 문제를 다른 순서로 처리해야 합니다. 반대로 깊이가 작고 구조가 재귀적이라면 불필요한 변환보다 명확한 재귀 구현이 유지보수에 유리합니다.

두 구현을 비교할 때는 같은 종료 조건과 같은 작업 순서를 수행하는지도 확인해야 합니다. 재귀를 반복으로 바꾸는 과정에서 방문 순서가 달라지거나 상태 복원 단계가 빠지면 결과가 달라질 수 있습니다. 특히 트리 순회와 백트래킹에서는 하강할 때의 작업과 상승할 때의 작업을 구분하여 명시적 스택에 저장해야 합니다. 변환의 목표는 단순히 함수 호출을 없애는 것이 아니라 원래 알고리즘의 상태 전이를 그대로 보존하는 것입니다.

결정한 방식은 테스트에서도 검증해야 합니다. 빈 입력과 가장 작은 입력으로 종료 조건을 확인하고, 최대 입력으로 반복 횟수와 호출 깊이가 예상 범위 안에 있는지 살펴봅니다. 이렇게 하면 논리 오류와 자원 한계 문제를 함께 발견할 수 있습니다.
