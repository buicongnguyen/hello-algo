# 시간 복잡도

실행 시간은 알고리즘 효율을 직관적으로 보여 줍니다. 코드의 실행 시간을 정확히 추정하려면 다음과 같은 절차가 필요합니다.

1. 하드웨어, 프로그래밍 언어, 운영체제 같은 **실행 플랫폼을 결정**합니다.
2. 덧셈 `+`, 곱셈 `*`, 출력 `print()` 등 **각 연산에 필요한 시간을 측정**합니다.
3. 코드에서 수행되는 **모든 연산의 횟수를 세고** 각 연산 시간의 합을 구합니다.

예를 들어 다음 코드의 입력 크기를 $n$이라고 합시다.

```python
# 잠긴 원문의 정확한 실행 시간 계산 예제가 삽입됩니다.
```

위 방식으로 계산하면 실행 시간은 $(6n + 12)$ ns입니다.

$$
1 + 1 + 10 + (1 + 5) \times n = 6n + 12
$$

하지만 **알고리즘의 정확한 실행 시간을 일일이 세는 방식은 실용적이지 않습니다.** 알고리즘은 서로 다른 플랫폼에서 실행되어야 하므로 추정치를 특정 장비에 묶고 싶지 않습니다. 또한 모든 연산의 실제 비용을 정확히 알기 어렵고, 캐시나 컴파일러 최적화처럼 단순 합산으로 설명하기 어려운 요소도 있습니다.

## 시간 성장 추세 세기

시간 복잡도는 실행 시간의 정확한 값을 세는 대신 **데이터 크기가 증가할 때 실행 시간이 어떤 추세로 성장하는지**를 셉니다.

입력 크기가 $n$이고 알고리즘 `A`, `B`, `C`가 있다고 합시다.

```python
# 잠긴 원문의 세 알고리즘 비교 예제가 삽입됩니다.
```

- `A`는 출력 연산을 $1$번만 수행하므로 $n$이 커져도 실행 횟수가 늘지 않습니다. 이를 상수 차수라고 합니다.
- `B`는 출력 연산을 $n$번 반복하므로 실행 시간이 $n$에 비례해 증가합니다. 이를 선형 차수라고 합니다.
- `C`는 출력 연산을 $1000000$번 수행하여 실제로 오래 걸릴 수 있지만, 이 횟수는 $n$과 무관합니다. 따라서 `C`도 `A`와 같은 상수 차수입니다.

![알고리즘 A, B, C의 시간 성장 추세](time_complexity.assets/time_complexity_simple_example.png)

정확한 실행 시간을 세는 것과 비교하면 시간 복잡도에는 다음 특징이 있습니다.

- **알고리즘 효율을 효과적으로 평가합니다.** `B`는 $n > 1$이면 `A`보다 느리고, $n > 1000000$이면 `C`보다도 느립니다. 입력 크기가 충분히 크면 상수 차수는 결국 선형 차수보다 유리합니다.
- **유도 과정이 단순합니다.** 플랫폼과 개별 연산 종류는 성장 추세에 영향을 주지 않으므로 모든 기본 연산을 같은 단위 시간으로 보고 횟수만 셀 수 있습니다.
- **한계도 있습니다.** `A`와 `C`는 같은 복잡도이지만 실제 시간은 크게 다릅니다. 또한 $n$이 작을 때는 더 높은 차수의 `B`가 `C`보다 빠를 수 있습니다. 복잡도는 상수 비용을 숨기므로 작은 입력이나 같은 차수의 구현을 정밀 비교하려면 실제 측정이 필요합니다.

그럼에도 복잡도 분석은 입력 규모가 커질 때 나타나는 근본적인 효율 차이를 설명하는 가장 널리 쓰이는 방법입니다.

## 함수의 점근적 상한

다음 함수의 입력 크기를 $n$이라고 합시다.

```python
# 잠긴 원문의 연산 횟수 함수 예제가 삽입됩니다.
```

연산 횟수를 입력 크기 $n$의 함수 $T(n)$으로 쓰면 다음과 같습니다.

$$
T(n) = 3 + 2n
$$

$T(n)$은 선형 함수이므로 실행 시간의 성장 추세도 선형이며 시간 복잡도는 $O(n)$입니다. 이때 $O$를 <u>큰 O 표기</u>라고 하며, 함수 $T(n)$의 <u>점근적 상한</u>을 나타냅니다.

시간 복잡도 분석은 본질적으로 연산 횟수 $T(n)$의 점근적 상한을 찾는 과정입니다.

!!! note "함수의 점근적 상한"

    양의 실수 $c$와 $n_0$가 존재하여 모든 $n > n_0$에 대해 $T(n) \leq c \cdot f(n)$이면, $f(n)$을 $T(n)$의 점근적 상한으로 볼 수 있고 $T(n) = O(f(n))$으로 씁니다.

그림처럼 점근적 상한을 구한다는 것은 $n$이 무한히 커질 때 $T(n)$과 같은 성장 수준을 갖고 상수 계수 $c$만큼만 차이 나는 함수 $f(n)$을 찾는 것입니다.

![함수의 점근적 상한](time_complexity.assets/asymptotic_upper_bound.png)

후보 함수 $f(n)$을 선택할 때는 특정 입력 $n$에서의 정확한 값보다 충분히 큰 $n$에서의 성장 수준을 봅니다. 같은 연산 횟수에 대해 또 다른 $f(n)$을 상한으로 잡을 수도 있지만 가장 유용한 표기는 지배적인 성장 차수를 드러냅니다. 분할 수 $m$이나 입력 $n$의 작은 구간에서 생기는 차이는 상수로 흡수되고, $n$이 계속 커질 때 남는 형태가 비교 기준이 됩니다.

이 관점은 구현 언어나 CPU가 달라져도 유지됩니다. 플랫폼 차이는 실행 시간을 일정 배율로 빠르게 하거나 느리게 할 수 있지만, 입력이 반복해서 커질 때 연산량이 증가하는 구조 자체는 바꾸지 않습니다. 따라서 점근 표기는 실제 시간의 예측식이 아니라 확장 가능성을 설명하는 분류입니다.

## 유도 방법

점근적 상한의 정의가 수학적으로 느껴지더라도 먼저 계산 절차를 익힐 수 있습니다. 함수 $f(n)$을 정하면 시간 복잡도 $O(f(n))$을 얻습니다. 전체 과정은 연산 횟수를 센 뒤 점근적 상한을 결정하는 두 단계입니다.

### 1단계: 연산 횟수 세기

코드를 위에서 아래로 읽으며 각 줄의 실행 횟수를 셉니다. $c \cdot f(n)$의 상수 계수 $c$는 어떤 양의 값도 될 수 있으므로 **$T(n)$의 상수항과 계수는 복잡도 차수에 영향을 주지 않습니다.**

1. **$T(n)$의 상수를 무시합니다.** 상수는 $n$과 독립적이어서 성장 추세를 바꾸지 않습니다.
2. **모든 계수를 생략합니다.** $2n$번이나 $5n + 1$번 반복해도 계수와 상수항을 버리면 모두 $n$번으로 단순화할 수 있습니다.
3. **중첩 루프는 곱합니다.** 전체 연산 횟수는 바깥과 안쪽 루프의 횟수를 곱한 값이며, 각 층에서 앞의 단순화 규칙을 따로 적용합니다.

다음 함수에 이 규칙을 적용해 연산 횟수를 셉니다.

```python
# 잠긴 원문의 연산 횟수 계산 예제가 삽입됩니다.
```

완전한 계산과 단순화한 계산은 모두 $O(n^2)$을 도출합니다.

$$
\begin{aligned}
T(n) & = 2n(n + 1) + (5n + 1) + 2 & \text{완전한 계산} \newline
& = 2n^2 + 7n + 3 \newline
T(n) & = n^2 + n & \text{단순화한 계산}
\end{aligned}
$$

### 2단계: 점근적 상한 결정

**시간 복잡도는 $T(n)$의 최고차항이 결정합니다.** $n$이 무한히 커지면 최고차항이 지배하고 다른 항의 영향은 상대적으로 사라집니다.

다음 표는 계수가 아무리 커도 성장 차수를 바꾸지 못한다는 사실을 강조합니다.

표: 연산 횟수와 시간 복잡도

| 연산 횟수 $T(n)$ | 시간 복잡도 $O(f(n))$ |
| --- | --- |
| $100000$ | $O(1)$ |
| $3n + 2$ | $O(n)$ |
| $2n^2 + 3n + 2$ | $O(n^2)$ |
| $n^3 + 10000n^2$ | $O(n^3)$ |
| $2^n + 10000n^{10000}$ | $O(2^n)$ |

$$
\begin{aligned}

!!! tip "로그 표기의 밑은 무엇인가요?"

    표기 $O(\log n)$의 밑을 살펴봅시다. 엄밀히 말해 매번 $m$개로 나누면 시간 복잡도는 $O(\log_m n)$입니다. 로그 밑 변환 공식을 적용하면 서로 다른 밑의 복잡도가 같습니다.

    $$
    O(\log_m n) = O(\log_k n / \log_k m) = O(\log_k n)
    $$

    밑 $m$은 상수 계수로 변환되어 복잡도에 영향을 주지 않으므로 보통 밑을 생략하고 $O(\log n)$으로 씁니다.

### 팩토리얼 차수 $O(n!)$

팩토리얼 차수는 순열 문제에 대응합니다. 서로 다른 $n$개 원소의 모든 배열 방법 수는 다음과 같습니다.

$$

$$

## 최악, 최선, 평균 시간 복잡도

**알고리즘의 시간 효율은 입력 데이터 분포에 따라 달라질 수 있습니다.** 길이 $n$인 배열 `nums`에 $1$부터 $n$까지의 수가 한 번씩 무작위 순서로 들어 있고, 값 $1$의 인덱스를 찾는다고 합시다.

- `nums = [?, ?, ..., 1]`처럼 $1$이 마지막에 있으면 배열 전체를 순회하여 **최악 시간 복잡도 $O(n)$**에 도달합니다.
- `nums = [1, ?, ?, ...]`처럼 $1$이 첫 위치에 있으면 배열 길이와 무관하게 즉시 종료하여 **최선 시간 복잡도 $\Omega(1)$**에 도달합니다.

최악 시간 복잡도는 점근적 상한이며 큰-$O$로, 최선 시간 복잡도는 점근적 하한이며 $\Omega$로 나타냅니다.

최선 경우는 매우 낮은 확률의 특별한 입력에서만 나타날 수 있어 실제 평가에서는 거의 사용하지 않습니다. **최악 시간 복잡도는 효율의 안전한 상한을 제공하므로 더 실용적입니다.**

최악과 최선 역시 특정 분포만 설명합니다. 무작위 입력에서의 실행 효율은 <u>평균 시간 복잡도</u>가 더 잘 나타내며 $\Theta$ 표기를 사용합니다.

입력 분포를 정의하지 않은 “평균”은 의미가 불분명합니다. 가능한 입력이 같은 확률로 나타나는지, 실제 서비스에서 특정 패턴이 더 자주 나타나는지에 따라 기댓값이 달라집니다. 그래서 평균 복잡도를 제시할 때는 확률 가정도 함께 설명해야 합니다.

최악 경우는 드물게 발생하더라도 시스템의 응답 시간 한도나 자원 예약을 설계할 때 중요합니다. 반면 사용자 경험이나 장기 처리량을 예측할 때는 실제 입력 분포를 반영한 평균 분석이 더 유용할 수 있습니다. 어느 표기를 사용하든 분석 대상, 입력 가정과 보장하려는 범위를 함께 밝히면 복잡도 숫자가 전달하는 의미가 분명해집니다.

같은 알고리즘도 조기 종료 조건이나 데이터의 정렬 상태에 따라 실제 반복 횟수가 달라집니다. 최악 분석은 가능한 가장 긴 경로를 추적하고, 평균 분석은 각 경로가 나타날 확률까지 고려합니다. 이 구분을 유지하면 한 번의 빠른 실행을 전체 효율로 일반화하거나, 드문 최악 입력만으로 평상시 성능을 오해하는 일을 피할 수 있습니다.

위 예제에서는 값 $1$이 각 위치에 나타날 확률이 같으므로 평균 반복 횟수는 배열 길이의 절반인 $n / 2$이고, 평균 시간 복잡도는 $\Theta(n / 2) = \Theta(n)$입니다.

더 복잡한 알고리즘에서는 입력 분포 전체에 대한 수학적 기댓값을 구하기 어려울 수 있습니다. 이때는 보통 최악 시간 복잡도를 효율 판단 기준으로 사용합니다.

!!! question "평균 복잡도 기호가 자주 보이지 않는 이유는 무엇인가요?"

    $\Theta$ 기호보다 큰-$O$ 표기가 널리 알려져 평균 경우에도 관습적으로 쓰이는 경우가 많기 때문입니다. 하지만 엄밀히는 표준적인 사용이 아닙니다. “평균 시간 복잡도 $O(n)$”이라는 표현을 만나면 문맥상 $\Theta(n)$을 뜻하는지 확인해야 합니다.
