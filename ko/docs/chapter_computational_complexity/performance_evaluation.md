# 알고리즘 효율 평가

알고리즘을 설계할 때는 보통 다음 두 목표를 순서대로 추구합니다.

1. **문제의 해답 찾기**: 명시된 입력 범위에서 항상 올바른 결과를 얻어야 합니다.
2. **더 나은 해답 찾기**: 같은 문제를 해결하는 방법이 여러 개라면 가능한 한 효율적인 알고리즘을 선택합니다.

즉, 정확하게 문제를 해결한다는 전제 아래에서는 효율이 알고리즘의 품질을 판단하는 핵심 기준이 됩니다. 효율은 크게 두 차원으로 나뉩니다.

- **시간 효율**: 알고리즘을 실행하는 데 필요한 시간입니다.
- **공간 효율**: 실행 중 알고리즘이 차지하는 메모리 공간입니다.

목표는 “빠르면서도 메모리를 적게 사용하는” 자료구조와 알고리즘을 설계하는 것입니다. 효율을 제대로 평가할 수 있어야 여러 해법을 공정하게 비교하고, 병목을 찾아 설계와 구현을 개선할 수 있습니다. 평가 방법은 크게 실제 테스트와 이론적 추정으로 나뉩니다.

## 실제 테스트

같은 문제를 푸는 알고리즘 `A`와 `B`가 있다고 합시다. 가장 직접적인 비교 방법은 한 컴퓨터에서 두 알고리즘을 실행하고 실행 시간과 메모리 사용량을 측정하는 것입니다. 이 방법은 실제 동작을 반영하지만 결과를 일반화하기 어렵다는 한계가 있습니다.

첫째, **테스트 환경의 영향을 완전히 제거하기 어렵습니다.** CPU 종류와 코어 수, 메모리 대역폭, 캐시, 운영체제, 컴파일러와 언어 런타임이 모두 결과에 영향을 줍니다. 병렬성이 높은 알고리즘은 다중 코어 CPU에서 유리하고, 메모리 접근이 많은 알고리즘은 빠른 메모리와 큰 캐시에서 더 큰 이점을 얻습니다. 따라서 한 장비에서 빠른 구현이 다른 장비에서도 반드시 빠르다고 단정할 수 없습니다.

공정한 결론을 얻으려면 동일한 조건을 반복하고 여러 플랫폼에서 측정한 뒤 평균과 분산까지 확인해야 합니다. 하지만 이 과정은 비용이 크며, 특정 환경의 숫자를 알고리즘 자체의 특성으로 잘못 해석할 위험도 있습니다.

둘째, **충분한 범위의 입력을 테스트하려면 많은 자원이 필요합니다.** 입력 크기에 따라 상대적인 성능이 바뀔 수 있습니다. 작은 입력에서는 `A`가 빠르지만 큰 입력에서는 `B`가 앞설 수 있고, 데이터의 정렬 상태나 값 분포에 따라서도 결과가 달라질 수 있습니다. 설득력 있는 결론을 내려면 다양한 크기와 분포를 반복해서 시험해야 하므로 시간과 계산 자원이 많이 듭니다.

실제 테스트는 구현의 상수 비용, 캐시 동작, 런타임 특성을 확인하는 데 꼭 필요합니다. 다만 그것만으로 모든 입력 크기와 플랫폼에서의 효율을 설명할 수는 없습니다.

측정 결과를 해석할 때는 준비 단계와 핵심 알고리즘 단계도 분리해야 합니다. 파일 읽기, 네트워크 대기, 런타임 초기화까지 한꺼번에 측정하면 알고리즘이 아니라 주변 작업의 비용을 비교하게 될 수 있습니다. 또한 한 번의 실행값보다 여러 번의 반복 결과를 보고, 워밍업이나 백그라운드 작업으로 생긴 이상치를 구분해야 합니다. 이러한 원칙은 벤치마크의 신뢰도를 높이지만 테스트 설계의 비용도 함께 늘립니다.

## 이론적 추정

실제 테스트의 한계를 보완하기 위해 실행 전에 이론적으로 효율을 평가할 수 있습니다. 이 방법을 <u>점근적 복잡도 분석</u>, 줄여서 <u>복잡도 분석</u>이라고 합니다.

복잡도 분석은 알고리즘 실행에 필요한 시간·공간 자원과 입력 데이터 크기의 관계를 나타냅니다. 핵심은 **입력 크기가 증가할 때 필요한 시간과 공간이 어떤 추세로 성장하는지**를 설명하는 것입니다. 이를 세 부분으로 나누어 이해할 수 있습니다.

- “시간과 공간 자원”은 각각 <u>시간 복잡도</u>와 <u>공간 복잡도</u>에 대응합니다.
- “입력 데이터 크기가 증가할 때”라는 말은 효율을 하나의 고정된 입력이 아니라 입력 규모의 함수로 본다는 뜻입니다.
- “성장 추세”는 정확한 초 단위 시간이나 바이트 수보다, 입력이 커질 때 자원 사용량이 얼마나 빠르게 증가하는지에 주목한다는 뜻입니다.

**복잡도 분석은 실제 테스트의 여러 약점을 극복합니다.**

- 코드를 실제로 실행하지 않고도 비교할 수 있어 반복 측정에 필요한 계산 자원을 줄입니다.
- 특정 하드웨어나 운영체제에 종속되지 않아 분석 결과를 여러 실행 플랫폼에 적용할 수 있습니다.
- 다양한 데이터 크기, 특히 매우 큰 입력에서 알고리즘 효율이 어떻게 달라질지 설명합니다.
- 구현 세부의 작은 차이보다 알고리즘 구조에서 오는 근본적인 성장 차이를 드러냅니다.

!!! tip

    복잡도라는 개념이 아직 추상적으로 느껴져도 괜찮습니다. 뒤의 절에서 연산 횟수와 메모리 사용량을 실제 예제로 계산하며 단계별로 설명합니다.

복잡도 분석은 알고리즘 효율을 재는 “자”와 같습니다. 같은 기준으로 여러 해법의 시간과 공간 비용을 비교하고, 입력 규모가 커졌을 때 어느 설계가 더 안전한지 판단하게 해 줍니다.

이론적 분석과 실제 테스트는 경쟁 관계가 아니라 서로 보완합니다. 분석은 성장 차수가 나쁜 후보를 구현 전에 걸러 내고, 테스트는 같은 차수 안에서 상수 비용과 플랫폼 특성을 확인합니다. 먼저 문제 크기가 커질 때의 위험을 복잡도로 판단하고, 그다음 대표 입력과 실제 환경에서 측정하면 두 방법의 장점을 함께 얻을 수 있습니다.

평가 기준은 문제의 요구 사항과도 연결해야 합니다. 대화형 서비스는 평균 처리량보다 응답 지연의 상한이 중요할 수 있고, 일괄 처리 시스템은 전체 처리량을 우선할 수 있습니다. 메모리 제한이 엄격한 장치에서는 조금 느리더라도 최고 점유 공간이 작은 해법이 더 안전합니다. 같은 측정값도 목표가 무엇인지에 따라 해석과 선택이 달라집니다.

수학적 표기 때문에 초보자에게 어렵게 보일 수 있지만, 자료구조나 알고리즘의 특징을 설명할 때 실행 속도와 공간 사용량을 피하기는 어렵습니다. 그러므로 본격적으로 다음 장들을 읽기 전에 **간단한 코드의 복잡도를 분석할 수 있을 정도의 기초 감각을 먼저 갖추는 것**이 좋습니다.
