# 요약

### 핵심 내용

**알고리즘 효율 평가**

- 시간 효율과 공간 효율은 알고리즘 성능을 평가하는 두 핵심 지표입니다.
- 실제 테스트는 구현의 실제 동작을 보여 주지만 테스트 환경의 영향을 제거하기 어렵고, 다양한 입력 규모를 시험하려면 많은 자원이 필요합니다.
- 복잡도 분석은 플랫폼과 무관한 성장 추세를 보여 주므로 실제 테스트의 한계를 보완합니다.

**시간 복잡도**

- 시간 복잡도는 입력 크기가 증가할 때 실행 시간이 어떻게 성장하는지를 측정합니다. 작은 입력이나 같은 차수의 알고리즘 사이에서는 실제 속도를 정밀하게 비교하지 못할 수 있습니다.
- 최악 시간 복잡도는 큰-$O$ 표기로 나타내며, 함수의 점근적 상한에 대응합니다. 연산 횟수 $T(n)$이 $n$이 커질 때 어느 수준으로 성장하는지 표현합니다.
- 계산은 연산 횟수를 세는 단계와 그 식의 점근적 상한을 결정하는 단계로 나뉩니다.
- 대표적인 시간 복잡도는 낮은 순서대로 $O(1)$, $O(\log n)$, $O(n)$, $O(n \log n)$, $O(n^2)$, $O(2^n)$, $O(n!)$입니다.
- 입력 분포에 따라 실행 시간이 달라지는 알고리즘은 최악, 최선, 평균 시간 복잡도를 구분합니다. 최선 경우는 엄격한 조건에서만 나타나므로 실제 평가에서는 드물게 사용합니다.
- 평균 시간 복잡도는 무작위 입력에서의 효율을 설명하지만, 입력 분포와 수학적 기댓값을 분석해야 하므로 계산이 어려울 수 있습니다.

**공간 복잡도**

- 공간 복잡도는 입력 크기가 증가할 때 알고리즘이 사용하는 메모리의 성장 추세를 측정합니다.
- 실행 관련 공간은 입력, 임시, 출력 공간으로 나뉩니다. 보통 입력 공간은 계산에서 제외하고 임시 공간과 출력 공간을 봅니다. 임시 공간에는 임시 데이터, 스택 프레임, 명령어 공간이 포함되며 재귀에서는 스택 프레임이 특히 중요합니다.
- 메모리는 미리 확보해야 하는 하드 요구 사항이므로 일반적으로 최악 공간 복잡도에 집중합니다.
- 대표적인 공간 복잡도는 낮은 순서대로 $O(1)$, $O(\log n)$, $O(n)$, $O(n^2)$, $O(2^n)$입니다.

복잡도는 절대 실행 시간이나 절대 메모리 크기가 아니라 성장 등급을 비교하는 도구입니다. 동일한 차수 안에서는 상수 비용과 구현 세부가 중요할 수 있지만, 입력이 충분히 커지면 성장 차수가 선택을 지배합니다. 또한 시간과 공간을 동시에 최소화하기 어려우므로 실제 제약에 맞춰 어느 자원을 우선할지 결정해야 합니다.

분석 과정에서는 먼저 입력 크기가 무엇인지 명확히 정의해야 합니다. 정수 하나를 입력받는 함수에서는 그 값이 크기일 수 있고, 배열을 입력받는 함수에서는 원소 수가 크기입니다. 그런 다음 각 문장이 실행되는 횟수, 동시에 살아 있는 임시 데이터와 호출 프레임을 셉니다. 시간은 전체 작업량을 더하거나 중첩 구조에서 곱하고, 공간은 실행 중 최고점에 동시에 존재하는 메모리를 봅니다.

복잡도 표기는 알고리즘을 자동으로 선택해 주지는 않습니다. 정확성, 입력 분포, 지연 시간 목표, 메모리 한도와 구현 난이도를 함께 고려해야 합니다. 큰 입력이 가능한 서비스에서는 최악 경우가 안전한 기준이 되고, 작은 고정 입력에서는 단순한 구현의 상수 비용이 더 중요할 수 있습니다. 이론적 분석으로 후보를 좁힌 뒤 실제 환경에서 벤치마크하면 더 신뢰할 수 있는 결정을 내릴 수 있습니다.

반복과 재귀도 같은 기준으로 비교할 수 있습니다. 두 방식의 시간 성장 추세가 같아도 재귀는 반환되지 않은 호출의 문맥을 보존하므로 최고 메모리 사용량이 더 클 수 있습니다. 재귀가 문제 구조를 더 명확하게 표현하는지, 호출 깊이가 환경 제한을 넘는지, 명시적 스택으로 바꿀 때 가독성이 유지되는지를 함께 판단해야 합니다.

분석 결과에는 입력 크기의 정의와 최악·평균 중 어느 경우인지 함께 기록해야 다른 사람이 같은 결론을 재현할 수 있습니다.

### 질의응답

**질문:** 꼬리 재귀의 공간 복잡도는 $O(1)$인가요?

이론적으로 꼬리 호출 최적화를 적용하면 $O(1)$까지 줄일 수 있습니다. 하지만 Java, Python, C++, Go, C# 등 많은 환경은 자동 최적화를 보장하지 않으므로 일반적으로는 호출 깊이에 비례하는 $O(n)$으로 분석합니다.

따라서 소스 코드가 꼬리 재귀 형태라는 사실만으로 상수 공간을 가정해서는 안 됩니다. 사용하는 컴파일러와 런타임이 최적화를 명시적으로 보장하는지 확인하고, 보장하지 않으면 일반 재귀와 같은 방식으로 스택 프레임을 계산합니다.

**질문:** 함수와 메서드는 어떻게 다른가요?

<u>함수</u>는 독립적으로 실행할 수 있고 필요한 매개변수를 명시적으로 받습니다. <u>메서드</u>는 객체 또는 클래스에 연결되어 있으며 호출한 객체에 암묵적으로 바인딩되어 인스턴스 데이터를 다룰 수 있습니다.

- C는 절차적 언어이므로 기본적으로 함수만 있지만 구조체와 관련 함수를 조합해 객체 지향적인 형태를 흉내 낼 수 있습니다.
- Java와 C#에서는 실행 코드가 주로 클래스의 메서드입니다. 정적 메서드는 특정 인스턴스 데이터에 접근하지 않으므로 함수와 비슷하게 동작합니다.
- C++와 Python은 절차적 함수와 객체 지향 메서드를 모두 지원합니다.

**질문:** “일반적인 공간 복잡도” 그림은 실제 점유 공간의 절댓값을 보여 주나요?

아닙니다. 그림은 절댓값이 아니라 성장 추세를 비교합니다. $n = 8$일 때 곡선의 높이가 수식값과 정확히 일치하지 않을 수 있는데, 보기 좋은 범위로 압축하기 위한 상수항이 들어 있기 때문입니다.

상수 비용을 모르는 상태에서는 $n = 8$ 같은 작은 입력만으로 최적 해법을 고르기 어렵습니다. 하지만 $n = 8^5$처럼 입력이 커지면 성장 추세가 상수 차이를 압도하여 선택이 분명해집니다.

그림의 목적은 곡선의 상대적인 모양을 비교하는 것입니다. 눈금이나 특정 점의 높이는 설명을 위해 조정될 수 있으므로, 그래프에서 값을 읽어 실제 메모리 바이트를 예측해서는 안 됩니다.

**질문:** 실제 상황에 따라 시간이나 공간을 의도적으로 희생하기도 하나요?

그렇습니다. 실무에서는 공간을 더 사용해 시간을 줄이는 경우가 흔합니다. 데이터베이스의 B+ 트리나 해시 인덱스는 추가 메모리를 사용하는 대신 조회를 $O(\log n)$ 또는 $O(1)$로 빠르게 만듭니다.

반대로 임베디드 장치처럼 메모리가 매우 제한되면 해시 테이블 대신 배열 순차 탐색을 선택할 수 있습니다. 이 경우 검색 시간은 늘지만 공간 사용량을 줄일 수 있습니다.
