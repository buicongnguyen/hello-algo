# 4장 요약

### 핵심 복습

- 배열과 연결 리스트는 연속 저장과 분산 저장을 대표하며 장단점이 서로 보완됩니다.
- 배열은 `O(1)` 임의 접근과 낮은 구조 비용을 제공하지만 삽입·삭제는 보통 `O(n)`이고 길이가 고정됩니다.
- 연결 리스트는 위치를 알고 있을 때 연결만 바꾸어 `O(1)`에 삽입·삭제하고 유연하게 확장합니다. 대신 노드 접근은 `O(n)`이고 각 노드에 추가 메모리가 필요합니다.
- 대표적인 종류는 단일, 원형, 이중 연결 리스트입니다.
- 동적 리스트는 보통 동적 배열로 구현하는 순서 있는 집합입니다. 배열의 접근 장점을 유지하면서 용량을 자동으로 늘립니다.
- 동적 리스트 끝에 추가하는 연산의 분할 상환 비용은 `O(1)`이지만 한 번의 확장은 `O(n)`입니다.
- 디스크, RAM, 캐시는 속도, 용량, 비용 사이의 균형을 이루는 계층 구조입니다.
- 캐시 라인, 프리페치, 공간 지역성, 시간 지역성은 CPU가 RAM을 읽는 횟수를 줄입니다.
- 배열은 보통 연결 리스트보다 캐시 친화적이지만 최종 선택은 실제 요구 사항을 기준으로 해야 합니다.

배열과 연결 리스트의 장단점은 서로 보완적입니다. 연속 저장은 주소 계산과 캐시 활용에 유리하고, 분산 저장은 알려진 위치의 연결을 유연하게 수정할 수 있습니다. 동적 리스트는 배열에 자동 확장을 더해 사용성을 높이지만, 남는 용량과 가끔 발생하는 복사 비용까지 제거하지는 않습니다.

자료구조를 선택할 때에는 빅오 표기만 비교하지 말고 실제 작업 패턴을 확인해야 합니다. 임의 위치 접근과 전체 순회가 많다면 배열이 유리한 경우가 많고, 노드 참조를 이미 가진 상태에서 삽입과 삭제가 반복된다면 연결 리스트의 장점이 커집니다.

메모리 사용 방식도 선택의 일부입니다. 배열은 한 덩어리의 연속 공간과 확장을 위한 여유 용량이 필요하지만 원소마다 별도 연결을 저장하지 않습니다. 연결 리스트는 작은 메모리 블록을 유연하게 사용할 수 있지만 노드마다 참조와 할당 관리 비용이 붙습니다. 또한 연속 배치는 캐시 라인과 프리페치가 작동하기 쉬워 순차 처리의 실제 성능을 높일 수 있습니다.

### 질문과 답변

**스택에 놓인 배열과 힙 메모리에 놓인 배열의 효율은 같은가요?**

둘 다 원소를 연속해서 저장하므로 데이터 접근 효율은 비슷합니다. 하지만 스택 할당은 보통 빠르고 자동인 대신 용량이 작습니다. 힙 메모리는 더 크고 유연하지만 할당과 해제가 느릴 수 있고 단편화가 생기기 쉽습니다.

스택 배열은 보통 함수 호출 수명과 함께 자동으로 만들어지고 제거됩니다. 크기가 너무 크면 제한된 스택 공간을 넘을 수 있습니다. 힙 배열은 실행 중 필요한 크기를 결정하고 더 오래 유지할 수 있지만, 수동 관리 언어에서는 적절한 해제가 필요합니다. 어느 영역에 있든 배열 내부가 연속이라는 사실과 인덱스 주소 계산 방식은 같습니다.

그러므로 “스택이 항상 빠르다”거나 “힙 배열은 임의 접근이 느리다”라고 일반화하면 안 됩니다. 할당과 해제 비용, 사용 가능한 공간, 객체 수명에는 차이가 있지만 이미 만들어진 배열의 원소를 읽는 방식은 동일합니다. 어떤 차이를 논의하는지 명확히 구분해야 올바른 결론을 얻을 수 있습니다.

**배열 원소가 보통 같은 데이터형이어야 하는 이유는 무엇인가요?**

원소 크기가 같으면 다음 고정식으로 주소를 계산할 수 있습니다.

```text
# 원소 주소 = 배열 시작 주소 + 원소 크기 × 인덱스
```

원소마다 크기가 다르면 이 식만으로는 충분하지 않습니다. 연결 리스트는 참조를 따라 접근하므로 원칙적으로 노드마다 다른 종류의 데이터를 담을 수 있지만, 많은 구현은 타입 안전성을 위해 같은 데이터형을 사용합니다.

동일한 원소 크기는 컴파일러가 한 번의 곱셈과 덧셈으로 임의 위치 주소를 계산하게 합니다. 서로 다른 크기의 값을 직접 섞으려면 각 원소의 시작 위치를 별도로 기록하거나, 실제 객체 대신 크기가 같은 참조를 배열에 저장해야 합니다. Python 리스트가 여러 종류의 객체를 담으면서도 배열처럼 동작하는 이유가 바로 참조 배열이기 때문입니다.

고정된 원소 크기는 주소 계산뿐 아니라 메모리 정렬과 캐시 배치에도 유리합니다. 컴파일러는 각 인덱스가 차지하는 범위를 알고 반복문을 최적화할 수 있습니다. 참조 배열은 슬롯 크기를 일정하게 유지하는 대신 실제 값에 도달하려면 참조를 한 번 더 따라가야 하며, 객체 본체의 메모리 배치는 연속이라는 보장이 없습니다.

**노드 `P`를 삭제한 뒤 `P.next = None`으로 설정해야 하나요?**

머리 노드에서 더 이상 `P`에 도달할 수 없다면 알고리즘상 필수는 아닙니다. 그러나 복잡한 라이브러리나 자원 관리 시스템에서는 연결을 명시적으로 끊는 편이 더 안전하고 이해하기 쉽습니다.

외부 코드가 삭제된 `P`를 계속 참조한다면 `P.next`도 여전히 후속 노드를 가리킵니다. 이 연결이 논리 오류를 만들거나 후속 객체의 회수를 늦출 수 있으므로, 라이브러리 구현은 삭제된 노드를 명확한 독립 상태로 만드는 경우가 많습니다.

수동 메모리 관리 언어에서는 연결을 끊는 것과 메모리를 해제하는 것이 서로 다른 작업입니다. 참조를 비우기만 하면 메모리가 자동으로 반환되지 않을 수 있고, 반대로 다른 코드가 여전히 사용하는 노드를 먼저 해제하면 잘못된 주소를 읽게 됩니다. 자료구조의 논리적 삭제와 언어의 자원 관리 규칙을 함께 지켜야 합니다.

**위치를 찾는 데 $O(n)$이 드는데 왜 연결 리스트 삽입과 삭제를 $O(1)$이라고 하나요?**

$O(1)$은 위치를 이미 알고 있을 때 연결을 바꾸는 연산만 설명합니다. 먼저 노드를 찾아야 한다면 전체 시간은 $O(n)$입니다. 덱처럼 양 끝의 참조를 유지하는 구조는 많은 삽입과 삭제를 실제로 $O(1)$에 수행할 수 있습니다.

복잡도 설명에서는 연산의 입력 조건을 분명히 해야 합니다. “노드 뒤에 삽입”은 노드 참조가 입력으로 주어지는 연산이고, “인덱스 위치에 삽입”은 먼저 그 위치를 찾는 연산을 포함합니다. 같은 연결 리스트라도 두 인터페이스의 전체 비용은 다릅니다.

**노드 그림의 참조 부분은 메모리를 얼마나 사용하나요?**

그림은 정성적인 설명일 뿐입니다. 값의 크기는 `int`, `long`, `double`, 객체 같은 데이터형에 따라 달라지고 참조 크기는 운영체제와 컴파일 환경에 따라 보통 4바이트 또는 8바이트입니다. 따라서 그림 속 블록 크기만으로 정확한 비율을 알 수 없습니다.

객체 헤더, 정렬을 위한 패딩, 메모리 할당자의 관리 정보도 실제 크기에 영향을 줍니다. 작은 정수 하나를 저장하는 노드에서는 참조와 헤더가 값보다 훨씬 클 수 있지만, 큰 객체를 가리키는 노드에서는 상대적 비율이 달라집니다.

**동적 리스트 끝 추가는 항상 $O(1)$인가요?**

각 연산이 항상 그런 것은 아닙니다. 기반 배열이 가득 차면 $O(n)$ 할당과 복사가 필요합니다. 다만 용량을 일정 비율로 늘릴 때 여러 추가 연산의 분할 상환 비용은 $O(1)$입니다.

예를 들어 용량을 두 배로 늘리면 한 번 확장한 뒤 그만큼 많은 값싼 추가 연산을 수행할 여유가 생깁니다. 확장 비용을 그 사이의 모든 추가에 나누면 평균 비용이 상수로 유지됩니다. 실시간 시스템처럼 개별 연산의 최대 지연이 중요한 경우에는 드문 확장도 따로 고려해야 합니다.

필요한 최종 크기를 대략 알고 있다면 미리 용량을 예약해 확장 횟수를 줄일 수 있습니다. 반대로 큰 용량을 예약하고 실제로 적은 원소만 저장하면 공간을 낭비합니다. 분할 상환 복잡도는 긴 연산열의 평균 비용을 설명하므로 단일 요청의 지연 제한이나 순간 최대 메모리는 별도로 평가해야 합니다.

**동적 리스트에서 낭비되는 메모리는 어디에서 생기나요?**

리스트는 초기 용량을 갖고 $\times 1.5$ 같은 비율로 확장합니다. 확장 직후에는 사용하지 않는 칸이 남습니다. 크기와 용량을 관리하는 변수에도 작은 비용이 있지만 빈 칸이 주된 낭비입니다.

확장 비율이 크면 복사 횟수는 줄지만 평균 미사용 공간이 늘고, 비율이 작으면 공간은 아끼지만 더 자주 확장합니다. 표준 라이브러리는 일반적인 사용 패턴과 메모리 할당 비용을 고려해 이 비율을 선택합니다.

일부 구현은 원소가 많이 삭제되어도 용량을 즉시 줄이지 않습니다. 삭제할 때마다 축소하면 다시 추가할 때 곧바로 확장하는 진동이 생길 수 있기 때문입니다. 필요하다면 명시적인 축소 기능을 제공하거나 사용 패턴에 따라 일정 조건에서만 용량을 줄입니다.

**원소 객체가 연속해서 놓이지 않아도 Python 리스트는 배열인가요?**

그렇습니다. Python 리스트의 기반 배열은 객체 자체가 아니라 객체를 가리키는 참조를 연속해서 저장합니다. 그래서 실제 객체가 흩어져 있어도 인덱스의 참조를 $O(1)$에 얻을 수 있습니다.

따라서 연속인 것은 객체 주소를 담은 슬롯이지 객체 본체가 아닙니다. 인덱스로 슬롯을 읽은 뒤 그 참조를 한 번 더 따라가 실제 객체에 접근합니다. 서로 다른 리스트가 같은 객체를 가리키는 것도 가능하며, 가변 객체라면 한 경로의 변경이 다른 경로에서도 보일 수 있습니다.

**`[[0]] * n`은 서로 독립적인 하위 리스트 $n$개를 만드나요?**

아닙니다. 모든 원소가 같은 `[0]` 리스트를 가리킵니다. 독립된 리스트를 만들려면 리스트 컴프리헨션을 사용합니다.

곱셈 연산은 원소 객체를 깊은 복사하지 않고 같은 참조를 반복합니다. 따라서 한 하위 리스트에 값을 추가하면 모든 위치에서 같은 변경이 관찰됩니다. 리스트 컴프리헨션은 반복마다 새로운 하위 리스트 객체를 만들기 때문에 서로 독립적입니다.

```python
n = 4
independent = [[0] for _ in range(n)]
```

`[0] * n`에서도 여러 원소가 같은 작은 정수 객체를 참조할 수 있지만 정수는 불변입니다. 한 원소에 다시 값을 대입하면 그 위치의 참조만 바뀌므로 다른 위치는 변하지 않습니다.

가변성과 참조 공유를 함께 이해해야 합니다. 공유된 객체가 불변이면 새로운 값을 대입할 때 슬롯의 참조만 교체되지만, 공유된 객체가 가변이면 객체 내부를 수정하는 순간 그 객체를 보는 모든 참조에 변화가 나타납니다.

**많은 C++ 알고리즘 문제에서 `std::list`를 직접 사용하지 않는 이유는 무엇인가요?**

`std::list`는 이중 연결 리스트라서 원소마다 포인터 두 개가 추가로 필요하고 데이터가 연속해서 놓이지 않습니다. 보통 `std::vector`보다 메모리를 많이 사용하고 캐시 활용도도 낮습니다. 따라서 동적 배열을 우선 사용하고 노드 단위 삽입·삭제의 이점이 정말 중요할 때 연결 리스트를 선택합니다.

또한 많은 알고리즘은 임의 접근 반복자를 요구하거나 연속 메모리에서 더 단순하고 빠르게 구현됩니다. `std::list`는 기존 반복자 위치에서 삽입·삭제할 때 강하지만, 위치를 찾는 순회와 메모리 할당 비용을 포함하면 기대한 이점이 사라질 수 있습니다.

연결 리스트가 적합한지는 “중간 삽입이 있다”는 사실 하나로 결정되지 않습니다. 삽입 위치를 어떤 비용으로 찾는지, 원소 이동 비용이 노드 할당 비용보다 큰지, 데이터가 캐시에 얼마나 잘 들어오는지까지 살펴야 합니다. 대부분의 원소가 작고 순회가 잦은 문제에서는 동적 배열이 실용적인 기본 선택이 되지만, 안정적인 노드 주소나 빠른 연결 재배치가 핵심 요구라면 연결 리스트가 더 적합할 수 있습니다.
