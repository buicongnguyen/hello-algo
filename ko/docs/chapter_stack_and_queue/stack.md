# 스택

<u>스택</u>은 후입선출(Last In, First Out, LIFO) 원칙을 따르는 선형 자료구조입니다.

탁자 위에 접시를 한 장씩 쌓아 올린 모습을 떠올릴 수 있습니다. 한 번에 접시 하나만 움직일 수 있다면 맨 아래 접시를 꺼내기 전에 그 위의 접시를 차례대로 모두 꺼내야 합니다. 접시를 정수, 문자, 객체 같은 원소로 바꾸면 스택의 동작을 이해할 수 있습니다.

아래 그림에서 가장 최근에 추가된 원소가 있는 쪽을 **스택의 꼭대기(top)**, 반대쪽을 **바닥(bottom)**이라고 합니다. 꼭대기에 원소를 추가하는 연산을 **푸시(push)**, 꼭대기 원소를 제거하는 연산을 **팝(pop)**이라고 합니다. 스택의 중간이나 바닥을 직접 수정하지 않는다는 제한이 LIFO 순서를 보장합니다.

## 스택 구현

스택의 내부 동작을 이해하기 위해 직접 클래스를 구현해 봅시다.

스택은 LIFO를 지켜야 하므로 원소 추가와 삭제를 꼭대기에서만 허용합니다. 배열과 연결 리스트는 원래 여러 위치에서 삽입과 삭제를 지원하지만, **스택은 배열이나 연결 리스트의 인터페이스를 의도적으로 제한한 구조**로 볼 수 있습니다. 내부 저장 방식은 다르더라도 외부 사용자는 같은 푸시, 팝, 확인 연산만 봅니다.

## 두 구현 방식 비교

**지원 연산**

두 구현 모두 스택에 정의된 모든 연산을 제공합니다. 배열 구현은 내부적으로 임의 접근도 가능하지만 이는 스택 정의에 포함되지 않으며 일반적으로 사용하지 않습니다. 추상 인터페이스에 필요한 기능만 노출하면 호출 코드가 특정 저장 방식에 의존하지 않습니다.

**시간 효율**

배열 구현의 푸시와 팝은 미리 할당된 연속 메모리에서 일어나므로 캐시 지역성이 좋고 실제 실행 속도가 빠른 경우가 많습니다. 다만 푸시가 현재 용량을 넘으면 동적 배열을 확장하고 모든 원소를 복사해야 하므로 그 한 번은 $O(n)$까지 느려질 수 있습니다. 확장이 일정 비율로 드물게 일어나면 여러 푸시의 분할 상환 비용은 일정하게 유지됩니다.

연결 리스트는 노드 단위로 유연하게 확장되어 용량 증가를 위한 전체 복사가 없습니다. 대신 푸시할 때마다 보통 새 노드 객체를 만들고 링크를 갱신하므로 할당 비용이 들며, 노드가 메모리에 흩어져 캐시 활용이 낮을 수 있습니다. 이미 만들어진 노드 객체를 그대로 넣는 상황이라면 새 노드 생성 비용을 줄일 수 있습니다.

기본형 원소를 저장하는 일반적인 상황에서는 배열 구현이 확장 시 드물게 느려지는 대신 평균 성능이 높은 편이고, 연결 리스트 구현은 개별 연산 비용이 비교적 일정하다는 차이가 있습니다. 실제 선택에서는 최대 지연 시간, 원소 수 변화, 할당 비용을 함께 봐야 합니다.

비교할 때에는 “푸시와 팝이 상수 시간”이라는 결론의 전제도 구분해야 합니다. 연결 리스트 구현은 꼭대기 노드 참조를 이미 유지하고 있다는 전제에서 링크를 일정한 횟수만 바꿉니다. 배열 구현은 끝 위치를 꼭대기로 선택하고 확장이 일어나지 않는 일반 연산을 기준으로 합니다. 스택 바닥을 꼭대기로 잘못 선택하거나 배열 앞에서 원소를 움직이는 구현은 같은 추상 구조라도 기대한 성능을 얻지 못합니다.

성능이 중요한 코드에서는 예상 원소 수를 알 때 배열 용량을 미리 예약하여 확장 횟수를 줄일 수 있습니다. 반대로 원소 수가 크게 변하고 노드 객체가 다른 구조와 공유된다면 연결 리스트가 자연스러울 수 있습니다. 공개 인터페이스가 같으면 이러한 내부 선택을 호출 코드와 분리할 수 있다는 점도 추상 자료구조의 중요한 장점입니다.

**공간 효율**

동적 배열은 실제 원소 수보다 큰 초기 용량을 잡거나 확장할 때 용량을 두 배처럼 일정 비율로 늘리므로 사용하지 않는 칸이 생길 수 있습니다. **따라서 배열 기반 스택은 일부 예약 공간을 낭비할 수 있습니다.**

반면 연결 리스트는 빈 용량을 미리 예약하지 않지만 모든 노드가 다음 노드의 참조와 객체 관리 정보를 추가로 저장합니다. **연결 리스트 노드는 배열 원소 하나보다 더 많은 메모리를 사용할 수 있습니다.** 어느 방식이 항상 더 절약된다고 단정할 수 없으며, 값의 크기, 예약 용량, 참조 크기, 실행 환경을 고려해야 합니다.

## 스택의 대표적 활용

- **브라우저의 뒤로/앞으로 이동과 소프트웨어의 실행 취소/다시 실행**: 새 상태를 스택에 쌓고 가장 최근 상태부터 되돌립니다. 양방향 이동을 지원하려면 일반적으로 두 스택을 함께 사용합니다.
- **프로그램 메모리와 함수 호출 관리**: 함수를 호출할 때 반환 주소와 지역 변수 같은 문맥을 담은 스택 프레임이 쌓이고, 함수가 끝나면 가장 최근 프레임부터 제거됩니다.
- **재귀와 깊이 우선 탐색**: 재귀 호출 단계마다 새 프레임이 쌓이고 되돌아올 때 역순으로 제거됩니다. 명시적인 스택을 사용하면 같은 탐색을 반복문으로 구현할 수 있습니다.
- **표현식 계산과 괄호 검사**: 아직 닫히지 않은 연산자나 괄호를 저장했다가 가장 최근 항목과 먼저 대응시켜 중첩 구조를 검증합니다.

이 활용 사례의 공통점은 가장 최근에 생성된 문맥을 먼저 처리해야 한다는 것입니다. 문제의 처리 순서가 LIFO와 맞는지 확인하면 스택을 사용할 수 있는 상황을 쉽게 알아볼 수 있습니다.

스택을 사용하는 알고리즘을 추적할 때에는 각 단계 뒤의 꼭대기와 전체 원소 순서를 적어 보는 것이 좋습니다. 재귀 코드를 반복문으로 바꿀 때에는 함수 호출 프레임이 저장하던 매개변수, 현재 위치, 아직 처리하지 않은 분기를 명시적인 스택 원소에 모두 담아야 동일한 실행 순서를 재현할 수 있습니다.
