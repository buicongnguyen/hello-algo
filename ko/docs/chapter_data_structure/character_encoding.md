# 문자 인코딩 *

컴퓨터에서는 모든 데이터가 이진 형식으로 저장되며 문자 `char`도 예외가 아닙니다. 문자를 표현하려면 각 문자와 이진수 사이의 일대일 대응 관계를 정의한 **문자 집합**이 필요합니다. 문자 집합이라는 표가 있으면 컴퓨터는 이진수를 찾아 해당 문자로 변환할 수 있습니다.

## ASCII 문자 집합

<u>ASCII 코드</u>는 가장 오래된 문자 집합이며 정식 이름은 American Standard Code for Information Interchange입니다. 한 바이트의 하위 7비트를 사용해 문자 하나를 나타내므로 최대 128개의 서로 다른 문자를 표현할 수 있습니다. 아래 표처럼 영어 대문자와 소문자, 숫자 0~9, 문장 부호, 줄 바꿈과 탭 같은 제어 문자를 포함합니다.

![ASCII 코드](character_encoding.assets/ascii_table.png)

하지만 **ASCII는 영어만 표현할 수 있습니다.** 컴퓨터가 세계로 보급되면서 더 많은 언어를 표현하기 위한 <u>EASCII</u> 문자 집합이 등장했습니다. ASCII의 7비트를 8비트로 확장하여 256개의 서로 다른 문자를 표현합니다.

세계 여러 지역에서는 각 언어에 맞는 EASCII 문자 집합이 차례로 만들어졌습니다. 이 문자 집합들은 앞 128개 문자를 ASCII와 동일하게 정의하고, 뒤 128개 문자는 각 지역의 필요에 맞게 다르게 정의했습니다. 따라서 같은 바이트 값도 사용한 문자 집합에 따라 다른 문자로 해석될 수 있었습니다.

이 방식은 기존 영어 문서와의 호환성을 유지하면서 지역 문자를 추가한다는 장점이 있었습니다. 그러나 문서에 사용된 EASCII 변형을 함께 알려 주지 않으면 수신 측은 뒤쪽 128개 값을 올바르게 해석할 수 없습니다. 서로 다른 지역의 문자를 한 문서에 섞기도 어렵습니다. 문자 집합이 단순히 표의 크기만 늘리는 문제로 끝나지 않고, 송신자와 수신자가 같은 규칙에 합의해야 하는 통신 문제임을 보여 줍니다.

## GBK 문자 집합

시간이 지나면서 **EASCII의 문자 수도 많은 언어에 충분하지 않다는 사실이 드러났습니다.** 예를 들어 한자는 거의 십만 자에 이르며 일상에서도 수천 자를 사용합니다. 1980년 중국 국가표준화 관리 기관은 6,763자의 한자를 담은 <u>GB2312</u> 문자 집합을 발표했고, 중국어의 일반적인 컴퓨터 처리 요구를 대부분 충족했습니다.

그러나 GB2312는 일부 희귀 한자와 번체자를 처리하지 못했습니다. <u>GBK</u>는 GB2312를 확장한 문자 집합으로 총 21,886자의 한자를 포함합니다. GBK 인코딩에서는 ASCII 문자는 1바이트, 한자는 2바이트로 표현합니다. 이처럼 지역별 인코딩은 해당 언어에는 효율적이지만 여러 언어가 섞인 환경에서는 호환 문제가 남습니다.

가변 길이 규칙을 사용하는 GBK에서는 현재 바이트가 ASCII 문자 하나인지, 두 바이트 한자의 시작인지 구별해야 합니다. 프로그램이 파일의 인코딩을 잘못 추정하면 바이트 경계부터 어긋나 여러 문자가 연속해서 깨질 수 있습니다. 또한 다른 국가가 만든 문자 집합의 코드와 직접 호환되지 않으므로, 국제적인 소프트웨어는 언어별 변환 표를 계속 유지해야 했습니다.

## 유니코드 문자 집합

컴퓨터 기술이 빠르게 발전하면서 문자 집합과 인코딩 표준도 급증했고 여러 문제가 생겼습니다. 한편으로 각 문자 집합은 보통 특정 언어만 정의하여 다국어 환경에서 정상적으로 동작하지 못했습니다. 다른 한편으로 같은 언어에도 여러 표준이 존재했기 때문에, 두 컴퓨터가 서로 다른 인코딩을 사용하면 정보를 주고받을 때 문자가 깨졌습니다.

당시 연구자들은 이렇게 생각했습니다. **세계의 모든 언어와 기호를 포함할 만큼 완전한 문자 집합을 만들면 다국어 환경과 깨진 문자 문제를 함께 해결할 수 있지 않을까?** 이 생각에서 크고 포괄적인 문자 집합인 유니코드가 탄생했습니다.

<u>유니코드</u>는 이론적으로 백만 개가 넘는 문자를 수용할 수 있습니다. 세계 여러 언어의 문자와 기호를 하나의 문자 집합에 넣어 서로 다른 인코딩 표준 때문에 생기는 문제를 줄이는 것이 목적입니다. 1991년 발표된 뒤 새로운 언어와 문자를 계속 추가했으며, 2022년 9월 기준 여러 언어의 문자, 기호, 이모지를 포함해 149,186자를 수록했습니다.

유니코드는 각 문자에 고유한 **코드 포인트**, 즉 문자 식별자를 부여합니다. 범위는 U+0000부터 U+10FFFF까지이며 하나의 통일된 번호 공간을 만듭니다. 그러나 **유니코드 자체는 코드 포인트를 컴퓨터에 어떤 바이트 배열로 저장할지 정하지 않습니다.** 길이가 다른 코드가 한 문장에 함께 있을 때 어디까지가 한 문자인지 구분할 저장 규칙이 별도로 필요합니다.

여기서 문자 집합과 문자 인코딩을 구분해야 합니다. 유니코드 문자 집합은 “이 문자에는 어떤 번호를 부여하는가”를 정하고, UTF-8·UTF-16·UTF-32 같은 인코딩은 “그 번호를 어떤 바이트열로 저장하는가”를 정합니다. 하나의 코드 포인트도 선택한 인코딩에 따라 서로 다른 바이트열이 될 수 있지만, 디코딩이 끝난 뒤 가리키는 유니코드 문자는 같습니다.

가장 단순한 방법은 모든 문자를 같은 길이로 저장하는 것입니다. 아래 그림에서 “Hello”의 문자는 각각 1바이트, “算法”의 문자는 각각 2바이트를 차지합니다. “Hello 算法”의 모든 문자를 2바이트로 맞추고 높은 자리를 0으로 채우면 시스템은 2바이트마다 한 문자를 읽어 문장을 복원할 수 있습니다.

![유니코드 인코딩 예](character_encoding.assets/unicode_hello_algo.png)

하지만 ASCII가 보여 주듯 영어 문자는 1바이트면 충분합니다. 모든 문자를 2바이트로 저장하면 영어 문서 크기가 ASCII의 두 배가 되어 메모리를 낭비합니다. 따라서 코드 포인트를 명확하게 구분하면서도 자주 쓰는 문자는 짧게 저장하는 더 효율적인 유니코드 인코딩이 필요합니다.

## UTF-8 인코딩

UTF-8은 현재 국제적으로 가장 널리 사용되는 유니코드 인코딩입니다. **문자에 따라 1~4바이트를 사용하는 가변 길이 인코딩**입니다. ASCII 문자는 1바이트, 라틴 문자와 그리스 문자는 2바이트, 흔한 한자는 3바이트, 일부 희귀 문자는 4바이트를 사용합니다.

UTF-8의 규칙은 다음 두 경우로 나눌 수 있습니다.

- 1바이트 문자는 최상위 비트를 $0$으로 두고 나머지 7비트에 유니코드 코드 포인트를 넣습니다. ASCII 문자가 유니코드의 첫 128개 코드 포인트를 차지하므로 **UTF-8은 ASCII와 하위 호환됩니다.** 아주 오래된 ASCII 문서도 UTF-8로 그대로 해석할 수 있습니다.
- 길이가 $n$바이트인 문자($n > 1$)는 첫 바이트의 상위 $n$개 비트를 $1$로 두고 $(n + 1)$번째 비트를 $0$으로 둡니다. 두 번째 바이트부터는 각 바이트의 상위 2비트를 $10$으로 두고, 남은 모든 비트에 문자 코드 포인트를 채웁니다.

아래 그림은 “Hello 算法”의 UTF-8 인코딩입니다. 첫 바이트의 상위 $n$개 비트가 모두 $1$이므로, 시스템은 앞쪽의 $1$ 개수를 세어 문자 길이가 $n$바이트임을 알 수 있습니다.

그렇다면 뒤따르는 바이트의 상위 2비트를 왜 $10$으로 둘까요? 이 $10$은 검사 표지로 사용할 수 있습니다. 시스템이 잘못된 바이트부터 텍스트를 해석하기 시작하더라도 바이트 앞의 $10$을 보고 시작 위치가 잘못되었음을 빠르게 알아낼 수 있습니다.

$10$을 표지로 사용할 수 있는 이유는 UTF-8 규칙에서 한 문자의 첫 두 비트가 $10$일 수 없기 때문입니다. 반대로 첫 두 비트가 $10$이라고 가정하면 문자의 길이는 $1$이어야 하므로 ASCII에 해당합니다. 그러나 ASCII의 최상위 비트는 $0$이어야 하므로 가정과 모순됩니다.

이 자기 동기화 특성은 네트워크 전송이나 파일 일부가 손상되었을 때 특히 유용합니다. 중간 바이트부터 읽기 시작하더라도 연속 바이트의 표지를 확인해 잘못된 시작임을 알아내고 다음 문자 경계를 찾을 수 있습니다. 또한 ASCII 영역의 바이트 표현이 완전히 동일하므로 영문 중심의 기존 프로토콜과 도구를 바꾸지 않고도 유니코드 텍스트를 단계적으로 도입할 수 있었습니다.

![UTF-8 인코딩 예](character_encoding.assets/utf-8_hello_algo.png)

UTF-8 외에도 다음 두 유니코드 인코딩을 자주 사용합니다.

- **UTF-16**: 문자 하나를 2바이트 또는 4바이트로 표현합니다. ASCII와 자주 쓰는 비영어 문자는 2바이트, 일부 문자는 4바이트를 사용합니다. 2바이트 문자의 UTF-16 값은 유니코드 코드 포인트와 같습니다.
- **UTF-32**: 모든 문자를 4바이트로 표현합니다. 특히 ASCII 비율이 높은 문서에서는 UTF-8과 UTF-16보다 훨씬 많은 공간을 차지합니다.

저장 공간만 보면 영어는 1바이트만 필요한 UTF-8이 효율적입니다. 일부 비영어 문자, 예를 들어 흔한 한자는 UTF-16에서 2바이트지만 UTF-8에서는 3바이트일 수 있으므로 UTF-16이 더 작을 수 있습니다. 호환성 관점에서는 UTF-8이 가장 보편적이며 많은 도구와 라이브러리가 UTF-8을 우선 지원합니다.

따라서 모든 문서에 절대적으로 가장 작은 인코딩 하나가 존재하는 것은 아닙니다. 실제 공간 효율은 문서에 어떤 문자들이 얼마나 자주 등장하는지에 따라 달라집니다. 그럼에도 웹과 공개 데이터 교환에서는 기존 ASCII와의 호환성, 문자 경계 복구, 다양한 운영체제와 도구의 지원을 함께 고려해 UTF-8을 기본 선택으로 삼는 경우가 많습니다.

## 프로그래밍 언어의 문자 인코딩

과거 여러 프로그래밍 언어는 프로그램이 실행되는 동안 문자열을 UTF-16 또는 UTF-32 같은 내부 인코딩으로 저장했습니다. 고정 길이에 가까운 표현에서는 문자열을 배열처럼 다루기 쉽고 다음 장점이 있습니다.

- **임의 접근**: UTF-16 문자열은 위치를 계산해 쉽게 임의 접근할 수 있습니다. UTF-8은 가변 길이이므로 $i$번째 문자를 찾으려면 문자열 시작부터 $i$번째 문자까지 순회해야 하며 $O(n)$ 시간이 걸립니다.
- **문자 수 계산**: 임의 접근과 마찬가지로 UTF-16 문자열의 길이는 $O(1)$에 계산할 수 있습니다. UTF-8 문자열의 실제 문자 수를 계산하려면 전체 문자열을 순회해야 합니다.
- **문자열 연산**: 분할, 결합, 삽입, 삭제 같은 연산은 UTF-16 문자열에서 비교적 단순합니다. UTF-8에서는 잘못된 바이트 경계에서 문자열을 자르지 않도록 추가 계산이 필요합니다.

프로그래밍 언어의 문자 인코딩 설계는 역사와 실행 환경을 함께 반영합니다.

- Java의 `String`은 UTF-16을 사용합니다. Java 설계 초기에는 16비트면 모든 문자를 표현할 수 있다고 예상했지만, 이후 유니코드가 16비트를 넘어 확장되었습니다. 그래서 일부 문자는 두 개의 16비트 값인 **서러게이트 쌍**으로 표현합니다.
- JavaScript와 TypeScript 문자열도 UTF-16을 사용합니다. Netscape가 1995년에 JavaScript를 발표했을 때 유니코드는 개발 초기였고 당시에는 16비트로 충분하다고 보았습니다.
- C#은 .NET 플랫폼과 Windows를 포함한 Microsoft 기술이 UTF-16을 널리 사용하기 때문에 UTF-16을 채택했습니다.

문자 수를 과소평가한 이 언어들은 16비트를 넘는 유니코드 문자를 서러게이트 쌍으로 처리해야 했습니다. 문자열 안에서 한 문자가 2바이트 또는 4바이트를 차지하므로 고정 길이의 장점을 잃고, 추가 처리 코드 때문에 구현과 디버깅도 복잡해집니다.

따라서 문자열의 “길이”가 무엇을 뜻하는지 API마다 확인해야 합니다. 어떤 함수는 바이트 수를, 어떤 함수는 UTF-16 코드 단위 수를, 또 다른 함수는 유니코드 코드 포인트 수를 반환합니다. 사용자가 화면에서 하나로 인식하는 글자도 결합 문자나 이모지 조합 때문에 여러 코드 포인트로 구성될 수 있습니다. 문자열을 자르거나 커서를 이동할 때 저장 단위만 기준으로 삼으면 문자 중간을 분리할 수 있습니다.

이런 이유로 다른 저장 전략을 채택한 언어도 있습니다.

- Python의 `str`은 유니코드를 사용하며 문자열에서 가장 큰 코드 포인트에 따라 저장 단위를 유연하게 선택합니다. 모든 문자가 ASCII이면 문자당 1바이트, 모두 기본 다국어 평면 안에 있으면 2바이트, 그 범위를 넘는 문자가 있으면 4바이트를 사용할 수 있습니다.
- Go의 `string`은 내부적으로 UTF-8을 사용합니다. 하나의 유니코드 코드 포인트를 나타내는 `rune`형도 제공합니다.
- Rust의 `str`과 `String`은 내부적으로 UTF-8을 사용하고, 단일 유니코드 코드 포인트를 나타내는 `char`형을 제공합니다.

여기서 다룬 내용은 프로그래밍 언어가 실행 중 문자열을 저장하는 방법입니다. **파일에 문자열을 저장하거나 네트워크로 전송하는 방법과는 구분해야 합니다.** 파일과 네트워크에서는 보통 호환성과 공간 효율이 뛰어난 UTF-8로 문자열을 인코딩합니다.

프로그램 내부 표현과 외부 표현이 다르면 입출력 경계에서 반드시 인코딩과 디코딩이 일어납니다. 이때 문자 집합을 명시하고 오류 처리 정책을 정해야 합니다. “문자열은 이미 글자이므로 바이트 변환을 생각하지 않아도 된다”는 가정은 깨진 문자, 잘린 데이터, 보안 검증 우회 같은 문제로 이어질 수 있습니다.

안전한 프로그램은 입력의 인코딩을 명확히 확인하고 문자 경계를 보존한 채 변환합니다.
